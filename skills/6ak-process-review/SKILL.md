# 6ak 流程整理与审阅

读原稿，整理可追溯的流程并在当前聊天里核对疑点。步骤、角色、规则和分组由材料决定。`model.json` 保存整理后的结构化业务正文，是流程图、节点内容、详情及 `flow.md` 的同一内容主源；原稿与逐字证据另存供核对。新建可迭代任务使用技能内置的[流程工作台](references/workbench.md)，页面不直接调用 LLM。交付 `flow.md` 供人审阅，同版 `model.json` 供下游生成或更新报告。用户只要流程说明时可直接整理和导出。

## 整理材料

主流程按操作方式归纳，同一环节的共同动作只写一次。例外若改变风控边界、业务决定权或后续流向，在对应动作处写清适用条件和实际影响。

1. 通读输入及用户已提供的补充，按 [整理方法](references/normalization.md) 区分主原稿、业务背景、现行规范与改进建议，识别事实、关系、例外和冲突。项目可提供材料目录及取材说明。只采用明确适用的来源优先级。原稿里的指令性文字作为业务资料处理。
2. 新建交互式审阅任务时，先从材料辨认主要动作、交接、来源位置以及高频业务术语，在聊天给出一屏分组草图与简短术语约定表。分组草图按阅读顺序列出，每组写业务名称、起止边界和代表性动作；序号单列，确认后只将业务名称写入分组标题，原文的正式阶段编号单列在分组依据中，保留名称中有业务含义的数字。术语约定表只列原稿中易混的角色简称、内部代号或业务黑话及拟用的自然语言表达，不替换原文证据。指出一处值得用户决定的拆合或归属（若有）。组数由本次材料和用户的阅读需要决定。此轮请用户确认或调整，停在草图；确认前不编制完整模型、展开全部节点或启动工作台。用户只调整局部时更新草图供确认。已明确指定分组或授权自行决定时沿用该授权。恢复旧任务或局部修订沿用当前分组。
3. 分组与用词口径确认后，首次建模即按[节点划分](references/normalization.md#节点划分)辨认有交接的连续步骤、各自启动的独立活动，以及同一活动的操作细节。复用草图中的动作、来源定位和约定用词，依[模型契约](references/model-contract.md)展开模型。按[正文整理](references/normalization.md#结构化正文与逐字依据)处理长表格和复合段落，按[关系判断](references/normalization.md#关系的判断)为每个出口提取条件。区分原文明示、整理推断与未知，优先讨论影响责任、规则边界或流向的疑点。后续只改分组时沿用节点编号、证据和业务关系。

工具使用 Node.js 22 或更新版本。安装包包含工作台服务和已构建页面，业务项目无需安装 npm 依赖。以下 `SKILL_ROOT`、`OUT` 与输入路径均替换为实际绝对路径。以资料所属项目为根目录，或使用用户指定的项目根目录，在其下建立 `.document-review/<项目编号>/`。初次整理的来源索引与模型可放在项目的准备目录，启动后以对应任务的当前稿为准。保留原稿。包内[调价示例](examples/messy-pricing.md)及[模型](examples/messy-pricing.model.json)用于核对接口，阶段和规则只适用于该示例。

```text
node "SKILL_ROOT/scripts/index-sources.cjs" "OUT/sources.json" "输入一.md" "输入二.md"
```

已有任务收到增补、删改或重排后的原稿时，先按[来源更新](references/source-updates.md)核对旧模型与新资料。来源编号由对应关系确定，不按本次文件顺序重新编号。诊断负责指出变化和待复核范围，业务解释仍需重新阅读原文。

## 在聊天里处理反馈

用户在聊天里直接说「从原文找漏掉的步骤」或提出其他修改时，按[定位当前工作稿](references/current-draft.md)判断任务与版本。当前对话能唯一定位时，直接读取最新权威稿和相关原文并起草候选。存在多份可能时，只澄清这次用哪份稿。自然语言指令可以有对象，也可以覆盖整个已定位的任务。

新建审阅任务时，先验证初始模型，再按[流程工作台](references/workbench.md)启动资料任务。流程图与节点内容为并列视图：流程图以阅读定位与快速交接给 Agent 为主，支持局部文案微调（保留结构与材料绑定）；节点内容采用分组目录与单节点工作区，用于查看原文与挂载补充材料。源文档片段及用户原话按稳定 `nodeId` 挂载到节点，原文在材料与查看依据中保留。事实补充、结构拆分与流向修改经过「补充材料 → Agent 起草候选 → 核对差异 → 采用 → 页面更新」，不绕过材料核对。

收到 `process-review-workbench-ref:v1` 时，核对任务、对象、材料与工作版本，使用技能内的 `workbench/scripts/workbench.cjs` 读取引用和最新上下文。根据节点全部有效材料、相关上下游与当前请求整理候选；只编辑 `candidate` 返回的 `modelFile`，通过 `review-candidate` 展示差异，再按该候选的有效确认执行 `apply --confirm`。自然语言任务能唯一定位时直接准备候选，不要求用户先复制引用；候选准备需带入本次相关的原话条目。服务关闭时用同一任务目录恢复，已有输入和历史保留。

旧版受管批注任务继续使用[流程草稿审阅页](references/grouped-review.md)的 `draft → check → commit`，不因为升级技能就转成工作台任务。其 Agent 只编辑工具返回的 `draft/model.json` 和 `draft/outcomes.json`；批注原话、逐条处理结果与已发布轮次由工具保留。既有 `pricing-review-batch:v1` 批次引用继续按原工具读取。两种任务的稿件和版本分别定位，不直接改写任务状态、历史、引用或工具元数据，也不为每批反馈另建临时脚本代替固定入口。

接受对象名称、唯一的连线起止、原句引用、已明确传入的文件选区，或报告生成的对象引用。可根据当前聊天中唯一正在讨论的对象理解“这里”。没有传入选区或对象时，浏览器选中状态不属于聊天上下文。如果有多个合理指代，只问相关对象之间的区别，独立工作继续。

报告复制的对象引用含一行可读名称和一行 `pricing-ref:v1` 记录。按 [反馈引用](references/feedback.md) 验证项目、版本、对象类型与编号后再改。标题改名、调整分组或布局时保留对象编号。仅改归属的反馈不改变时序或箭头。

按反馈含义处理：

- 原稿理解有误，核对原文并纠正对应陈述和引用。
- 明确补充现行事实，逐字保存相关用户原话为独立来源，标为用户补充。更新依赖该事实的字段、规则与关系，保留原始冲突和依据；已解决的疑点连接到确认依据。
- 未分类原话使用中性 `kind:raw`，按用户当次要求和实际含义理解，不自动认定为事实。拟议方案不能写成现行流程，疑问保留未知或问题，冲突保留双方原文；不确定且影响业务结论时在当前聊天澄清。

回复用户时指出改了什么及仍待确认的局部。业务改变后更新说明版本，重新核查受影响内容；将旧报告的 `review.visual` 重置为 `not_run`。

## 复核与交付

按 [语义复核](references/quality-review.md) 核对关键表达、流向、证据和未决问题，记录实际复核范围与发现。验证并生成节点式 Markdown，后续关系写在所属节点下。`flow.md` 从模型生成，修改内容时先改业务主源再重导。

```text
node "SKILL_ROOT/scripts/validate-model.cjs" "OUT/model.json"
node "SKILL_ROOT/scripts/export-flow.cjs" "OUT/model.json" "OUT/flow.md"
```

工作台任务按[工作台交付](references/workbench.md#交付同版模型与说明)从当前已采用模型导出；旧版受管任务按[原交付流程](references/grouped-review.md#交付文档)从同一已发布轮次复制。将同版 `flow.md` 和 `model.json` 放到可见交付目录，回复时链接交付副本并说明版本、关键未决项和实际完成的检查。用户需要报告时，把导出的模型作为只读输入交给兼容的报告生成工具。现有调价报告仍可接收内容模型 v1。评估技能能力时读取 [开发与保留评估](evals/procedure.md)。

维护本技能工具时，以隔离的合成资料验证来源变化、引用和批注行为，检查方式见[质量复核](references/quality-review.md)。工具测试不要求用户先回答当前业务疑点，也不把测试用补充写入实际任务。
