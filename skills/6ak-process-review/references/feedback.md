# 对象引用与聊天反馈

用户可以说“在『重新提交申请』这个步骤，负责人是申请人”，或引用 `flow.md` 的节点标题、陈述或关系编号。若当前消息带有具体选区，先读当前文件并核对选中文本。选择本身只表达指代，后面的用户消息表达要做的修改。

报告中的复制操作会带出可读标题和一条定位记录，用户将这两行与自己的话一起发到聊天中。对象定位数据如下，真实记录里的摘要有完整 64 位。

```text
申请审批流程 · 节点「重新提交申请」
pricing-ref:v1 {"reportId":"approval-review","modelSha256":"<完整摘要>","type":"node","id":"resubmit"}
```

`type` 为 `node`、`relation`、`rule`、`issue` 或 `claim`。可读名称供人确认，定位依据为项目 ID、模型 SHA-256、对象类型和稳定 ID。摘要计算为 `SHA-256(JSON.stringify(model))`。读取范围只限用户此次要改的对象及受影响引用。

一条陈述可能出现在多个地方。`claim` 引用可带 `context` 对象，包含 `type`、`id` 及可选 `field`。通用陈述列表使用 `claimIds`，节点字段可用 `role`、`actions` 等裸键，规则参数可用 `value`、`basis` 等裸键，关系条件可用 `conditionClaimIds`，问题结论可用 `resolutionClaimIds`。核对反馈要更正共享事实，还是只调整此处的适用范围。局部变化可能要拆出新陈述并更新局部引用。

把引用作为纯文本交给定位工具，输入文件可以含对象标题和用户消息。每次校验一条引用。

```text
node "SKILL_ROOT/scripts/resolve-reference.cjs" "OUT/model.json" "引用文本.txt"
```

- 项目和版本匹配，定位到所引用对象及上下文。核对用户的改动意图后执行。
- 旧版引用，先从已知产物定位对应旧版，再按稳定 ID 对照当前对象。如果业务含义改变、对象被拆分或删除，说明差异并只问这一处。旧版不可获取时，请用户指出当前对象。
- 项目错配、对象不存在、类型或上下文不一致时，给出具体差异并请用户重新引用。不能把相近的名称或别的项目的同一编号当作同一对象。

用户明确补充现行事实时，仅保存与该事实相关的原话。使用单独的 `kind: "user-feedback"` 来源，保持旧证据范围、原稿和原冲突记录。对派生规则或改写后的总结使用相应的原话作为证据。除非用户确实明确了适用范围，否则保留范围缺口；将“比如”“以后可以”一类建议另记为方案。结构化引用本身只用于定位，不作为业务证据。
