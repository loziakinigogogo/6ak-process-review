# 在对话中定位当前工作稿

用户可在当前 Agent 对话里直接说「从原文找漏掉的步骤」。当对话已经指明一份工作稿时，回到该任务读取最新版本，核对原文并起草候选。

1. 先采用用户明确给出的任务目录、当前对话已核实的任务与类型，或属于这次任务的有效引用。已发布版、旧引用中的原轮次和旧候选供比较。读取当前版本时重新查询对应任务，保留原来的写入流程。
2. 只确认了资料所属项目时，可用下方只读命令核对项目中 `.document-review/` 的直接任务目录。明确指定独立目录的任务可用 `--task`。在对话已明确选用旧版受管审阅或流程工作台时，可以加 `--kind formal` 或 `--kind workbench`。确认任务后，在当前对话记录其绝对目录和类型，后续自然语言请求沿用该任务。
3. 多份工作稿都可能适用时，只问这次使用哪份，列出任务名或路径与类型。受管审阅和流程工作台即使源自同一个模型，也分别选择。未找到时，沿用已明确提供的模型创建新工作台任务；缺少任务与资料所属项目时再澄清位置。浏览位置、文件修改时间、交付副本及未采用草稿都不决定任务归属。遇到身份或版本无法核对的记录时先报告该记录，保留原文件。

```text
node "SKILL_ROOT/scripts/locate-draft.cjs" --project "PROJECT_ROOT"
node "SKILL_ROOT/scripts/locate-draft.cjs" --task "TASK"
```

两条命令均使用绝对路径。工具返回 `unique`、`ambiguous` 或 `not-found`，并列出 `kind` 与 `taskDirectory`。项目定位限于已知项目的直接任务，显式指定的正式旧任务可继续由正式工具核对迁移记录。已明确传入普通模型而尚未建立任务时，可读取该模型并在聊天里起草建议。

## 旧版受管审阅任务（formal）

调用已安装技能里的只读状态命令，验证任务身份。正式审阅轮次由受管任务维护。

```text
node "SKILL_ROOT/scripts/grouped-review.cjs" status "TASK"
```

- `draft.status` 为 `active` 时，以 `draft.modelFile` 为当前编辑稿，核对 `draft.baseRevision` 与当前 `revision`。与当前请求同一范围的编辑沿用这份草稿。草稿绑定其他批次时，可读该稿核对影响，在聊天中列出新请求的候选，保留该批次的模型和处理结果。
- 没有活跃草稿时，读取 `status` 所返回的任务目录下 `revisions/<revision>/model.json`。需要写候选时，用 `grouped-review.cjs draft "TASK"` 从这轮建立草稿。已有旧任务按正式工具核对位置。状态为 `stale`、`incomplete` 或 `committed-cleanup-pending` 时，核对最新发布基线并保留原草稿，按[草稿恢复](grouped-review.md#处理一个批次)处理。
- 只编辑同一范围内工具返回的候选文件，使用 `check` 校验，按节点、关系和来源向用户展示拟变动的内容。用户明确要求发布这批修订后，再依正式流程 `commit`。旧报告引用和批注分别沿用 `pricing-ref:v1`、`pricing-review-batch:v1` 的[定位规则](feedback.md)和[批次流程](grouped-review.md#处理一个批次)。

## 流程工作台（workbench）

- 权威工作稿位于该任务的 `workbench/state.json` 内的 `model`，版本以 `workRevision`（界面 `W`）与 `modelHash` 配对核对。`stateRevision` 同时包含布局等变化。对话收到 `process-review-workbench-ref:v1` 时，先确认任务目录与当前任务一致，再读原引用和最新工作稿。引用快照与 `buffers/`、待定编辑和候选供参考。
- 支持节点材料的工作台中，源文档片段与用户原话按 `nodeId` 独立挂载，是整理输入；生成的 `model` 是图、正文和预览共同的输出。读取引用 `context.materials` 的全部有效绑定及真实来源、`contentInputs` 的原话性质和版本，并核对当前模型与上下游。不得只从当前 `claimIds` 反推输入，因为被改写的陈述不代表原材料已删除。材料保存、旧表达草稿恢复、提醒或建议不等于业务事实采用。
- `contentInputs.kind=raw` 表示用户直接写入、未分类的原话，必须完整纳入本次整理上下文，不要求用户先补标题、栏目或性质，也不自动改成 `fact`。候选工具继续通过 `feedbackSources` 返回旧版明确事实来源，并通过 `rawMaterialSources` 返回未分类原话的稳定版本快照；两类快照均不会自动加入 `model.json`。`user-feedback` 是来源标记，不是事实认证。按当次要求与原话实际含义选择逐字证据、陈述与 coverage；未来建议不能改写为当前流程，疑问保留 unknown/issue，冲突保留双方依据，含混处在现有对话澄清。材料原话、版本及已有性质保持，不新增网页聊天、自动分类或长期对话记忆。
- 根据材料重新整理时，一并核对 `node.title` 的行动概括、`fields/claims` 完整正文及 `relations` 的条件与去向。模型 v1 没有独立摘要字段，不能添加未知字段或用裁剪正文替代完整陈述。保留逐字证据、推断前提、未知及冲突；材料和工作版本改变后重新读取、起草并核对候选，不能沿用过期确认。页面的材料输入不会直接改写模型，业务变更通过候选审阅与采用完成。
- 0.1.4 安装包自带 `SKILL_ROOT/workbench/scripts/workbench.cjs` 及页面资源。使用该脚本的 `status --task "TASK"`、`context [NODE_ID] --task "TASK"` 核对当前任务；服务关闭时执行 `serve --task "TASK"` 恢复同一任务，不重新导入模型。启动返回的本机地址是本次页面入口。旧服务缺少所需能力时先保留输入、停止该任务的旧服务，再以新安装版恢复；不要把请求发给另一个任务。
- 引用明确时用 `candidate --reference "REFERENCE_ID" --task "TASK"` 纳入引用中的原话版本。自然语言已定位对象时，先读 `context` 的全部有效材料，给 `candidate --input "INPUT_JSON" --task "TASK"` 传入本次相关原话的 `contentEntryIds`；没有原话输入时可省略 `--input`。不能裸建候选后自行伪造 `wb-content-*` 来源。具体命令见[工作台](workbench.md#起草核对与采用候选)。
- 核对候选基线后只编辑返回的 `modelFile`，必要时回读完整来源。使用 `review-candidate` 展示差异和摘要，按用户对同一候选的有效确认通过 `apply --confirm` 提交。服务、候选或材料版本发生变化时重新核对，不手改 state、metadata 或历史绕过检查。已安装技能无需维护仓库即可完成这条链路。

## 核查提案与依据

查漏时对照当前模型和本次适用的原文，列明新增步骤、需要修订的原节点字段、关系、依据与待确认事项。另有更新稿时按[来源更新](source-updates.md)核对差异。当前稿的批注、用户补充原话及待确认项要随实际改动核对，原稿、历史版本和冲突证据保留。用户的操作意图和随附草稿只用于理解任务；未分类原话可作为可追溯资料，但只有含义明确且适用的现行事实才能写入当前业务陈述，不能因为来源可引用就把建议、疑问或含混表述认定为事实。

涉及连线时核对关系类型、条件、原来的两端及其实际衔接。改接到新端点时，根据当前稿和原文核对新端点、原节点和原端点。只有实际受影响的字段才与关系改动一起列入候选，逐项展示前后变化及理由。缺少依据的影响保留为疑点，现行冲突继续并列。
