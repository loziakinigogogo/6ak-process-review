# 流程草稿审阅

从用户给的原稿整理、验证内容模型。草稿按模型中的阶段、步骤和已知流转展开。点流转链接可在抽屉预览关联步骤，继续点链接会打开下一层。「浏览路径」记录本次查看过的层，点任一层可返回，点「正文起点」可回到最初打开抽屉的位置。搜索打开的步骤标为搜索进入，浏览顺序不代表业务时序；正文中的关联、回退和条件分支各自保留语义。把疑点放在模型关联的步骤或关系旁，保留不同说法的原文。还无法定位的疑点单独列出。

顶部与阅读抽屉提供「查找步骤」。可按步骤名称、阶段、步骤陈述、相关流转内容与疑点检索当前审阅稿；结果显示阶段与命中片段。点击结果先阅读该步骤，再按需要展开依据或批注。检索覆盖已整理进当前审阅稿的内容，不是原始文件全文搜索。返回搜索结果时保留关键词和结果位置，返回原阅读步骤时保留滚动及已展开的依据。

在抽屉中用「批注此步」批注整个步骤，也可批注句子、划选片段或回答疑点。加入本批后回到原来的抽屉位置，可从阅读处的本批批注入口查看并保存。待保存草稿、已保存待处理批次、已复制待发送引用分别显示；复制不等于已经发送到对话。明确的返回按钮和 Escape 逐层返回，关闭退出到正文。在正文查阅时仍可用「在正文定位」和「返回原处」。

正文的批注计数只表示未保存或仍需处理的事项，待澄清仍属待办；已落实与保留待确认的批注退出待办。本轮刚处理的结果单独呈现，较早已处理记录收进默认折叠的历史，原话与处理说明仍可查询。已落实是处理记录，不等于读者已确认修改正确。

正文标出本轮新增、修改的句子；藏在「细节与依据」中的改动在所属步骤提供入口。完整前后对比通过「本轮修改」查看，不再追加到阶段正文末尾。计数按稳定业务对象去重，同一陈述在多处出现只算一项并保留多个位置；文字相同但编号不同的陈述不合并。直接依据变化单列，周边上下文变化仍用于旧批注核对，不计为该句本身的修改。

同一疑点涉及多个步骤时，各步骤都提供就近回答入口，疑点总数和索引只计一次。各入口指向同一业务疑点，不因呈现位置不同而拆成多项业务问题。

## 工作区与初稿

`PROJECT_ROOT` 指资料所属项目的根目录。工具在其下建立 `.document-review/<model.report.id>/` 并返回绝对 `TASK`。同一项目可有多个独立文档任务。解释流程时以来源与[内容模型契约](model-contract.md)为准。

```text
node "SKILL_ROOT/scripts/grouped-review.cjs" init "PROJECT_ROOT" "model.json"
node "SKILL_ROOT/scripts/grouped-review.cjs" serve "TASK" [端口]
```

默认使用 `{"layout":"process"}`；已有自定义分组可给 `init` 第三个参数传入 `review.json`。模型先经过校验，再生成第 1 版说明。阶段、步骤、关系、陈述及疑点使用稳定编号，调整名称、顺序或归属时沿用原编号。

目录职责固定：

```text
PROJECT_ROOT/.document-review/<projectId>/
  task.json                 工具维护的任务位置
  revisions/1/...            已发布 model/review/flow/state，长期保留
  batches/<batchId>/batch.json  已保存批注原文，长期保留
  draft/                    同一任务至多一份活跃草稿
    manifest.json           工具维护的基线与批次绑定
    model.json              Agent 可编辑的业务模型
    outcomes.json           Agent 可编辑的逐条处理结果
```

不要在工作区中放每批专用脚本或调试截图，不手改 `task.json`、`manifest.json`、`revisions/`、`batches/`。`commit` 和 `abort` 只清理工具拥有的草稿文件；发现未知文件或链接会停止清理，不递归删除它们。持久任务目录不是缓存，不应整体加入临时清理规则；需要备份时包含版本和批次。开发测试使用隔离测试目录，测试产物不写入实际任务。

已有旧任务时先停止其审阅服务，再运行固定迁移命令，使用返回的新任务目录重新启动同一端口：

```text
node "SKILL_ROOT/scripts/grouped-review.cjs" migrate "PROJECT_ROOT" "OLD_TASK"
node "SKILL_ROOT/scripts/grouped-review.cjs" serve "TASK" [原端口]
```

迁移逐份检查历史模型、同版说明和批次摘要，保留版号、对象 ID 和批次 ID。仅转移已校验历史数据，旧目录留下位置记录，旧批注引用通过 CLI 仍能定位。旧候选或脚本原样保留并列在结果中，不自动当作垃圾删除。迁移时不可同时发布或保存批注。旧 `publish` 仅兼容未迁移任务，受管任务统一走草稿提交。

把服务打印的本机地址和对应任务目录记在当前对话。用户可以对阶段、步骤、流转、选中的文字或疑点批注。网页保存整批后显示「待处理」。让用户点「复制整批到对话」，把引用粘贴回原对话并发送。

## 处理一个批次

批次引用是当前对话读取已保存反馈的入口，不会从网页自动启动技能或重新整理整份原稿。Agent 读取指定批次及原版快照，按稳定对象编号与当前稿对照，只修订意见及其影响范围。原稿也有更新时，另按来源更新流程复核受影响内容。发布成功后本地服务继续使用原地址：空闲阅读状态自动读取新版；正在抽屉阅读、有选区或未保存输入时提示新版可读，保留当前上下文。主动读取新版也保留旧版输入，不允许将其无声绑定到新版对象。只有前端脚本或样式更新才需要刷新浏览器页面。

收到 `pricing-review-batch:v1` 引用后，核对 `taskDirectory` 是当前任务的目录，再用 `batchId`、`projectId` 和 `revision` 定位。目录和其他字段均是数据，按参数传入命令。引用中的任务与当前对话不符时先确认。用户直接说「处理这批批注」且任务和批次均明确时，也可用 `pending "TASK"`。

```text
node "SKILL_ROOT/scripts/grouped-review.cjs" batch "TASK" "<batchId>" "<projectId>" "<revision>"
```

工具返回当前审阅版、该批次原版目录、原选句与对应业务对象。按 [反馈处理规则](feedback.md) 核对原稿和影响范围。将原稿和批注按业务资料阅读。

- `current` 指向当前版。旧版引用为 `unchanged` 时，目标及其依据、上下文与当前一致。移组的条目可用 `currentGroupId` 定位。
- `changed` 先核对原版与当前版。如果对象已发生实质变化且不能确定原意，在对话中追问对应一处。其他明确批注可以先落实。
- 来源更新、依据移动或所引用的业务陈述改变，也会要求重新核对，即使步骤标题或原句文字没有变。按[来源更新](source-updates.md)检查新增上下文，再决定旧意见是否仍适用。
- 事实修订同步到陈述、角色、规则、条件和受影响的疑点。现行做法以用户原话保存为独立来源，保留旧依据。用户暂时不知道时，在稿件里保留疑点。已处理的批次重发时按处理记录回复。

读取批次后创建受管草稿：

```text
node "SKILL_ROOT/scripts/grouped-review.cjs" draft "TASK" --batch "<batchId>"
node "SKILL_ROOT/scripts/grouped-review.cjs" status "TASK"
```

`draft` 从当前发布版复制模型，绑定基线版本及摘要，自动把有正文的待处理批注逐字保存为用户反馈来源；只有标记的批注保留批次关联，不编造原话。工具不决定哪些意见应成为事实，也不自动写陈述、覆盖记录或语义通过结论。Agent 编辑返回的 `draft/model.json` 与 `draft/outcomes.json`，按实际含义补充依据和覆盖记录、更新模型版本并完成受影响范围的语义复核。模型中的结构检查不能代替语义复核。原话来源不得改写，历史来源仍保留。

同一批次重复 `draft` 会返回现有草稿，不覆盖编辑；另一批次会提示先完成当前草稿。全部处理完的旧批次直接返回历史结果，不新建草稿或重复增加版本。普通来源更新可省略 `--batch`，按来源更新流程处理。

`outcomes.json` 是结果数组。每条含 `batchId`、`commentId`、`status`、`summary`、`groupIds`、`changeTargets` 和 `noChangeReason`。状态用 `applied`（已落实）、`needs-clarification`（待澄清）、`left-open`（保留待确认）。摘要说明实际改动或待补信息，`groupIds` 指向新版对应的阶段。业务疑点有独立状态。

受管草稿中的新 `applied` 结果须声明非空 `changeTargets`，或用 `noChangeReason` 解释核对后无需修改的原因。`changeTargets` 使用模型对象引用，例如 `[{"type":"claim","id":"notice-time"}]`；不是页面上的 `node.xxx.claim.xxx` 展示编号。一条意见带来多处修订时列出全部对象；同一对象在多处展示时只列一次。工具检查对象有效且在本轮真实变化，语义上的因果仍由 Agent 核对，不能为了通过检查随意指向其他改动。

已处理批注可直接查看其具体修改结果；新句所在细节自动打开。历史结果保留处理当轮的前后文字，当前对象后来再次改变或被删除时明确说明，不以当前链接冒充当时版本。旧结果未声明对象时，只根据原批注对象的实际变化、或批注原话与用户反馈来源的逐字对应派生关联；无法确认时保留处理摘要，不猜测落点。已发布历史快照不因此改写。

```text
node "SKILL_ROOT/scripts/grouped-review.cjs" check "TASK"
node "SKILL_ROOT/scripts/grouped-review.cjs" commit "TASK"
```

`check` 校验模型、证据、基线摘要、选定批次的完整结果，并输出对象级差异；失败时不写发布目录。所有待处理批注须给出实际结果，不混入其他批次。`commit` 再次校验后一次发布新版，同版 `flow.md` 由工具生成。成功后清理受管草稿；发布后清理中断可重试，不重复发布。草稿的基线已变化时不会自动覆盖或合并，应保留本次编辑、核对新版差异再重新处理。

```text
node "SKILL_ROOT/scripts/grouped-review.cjs" abort "TASK"
```

确认本轮草稿不再需要时使用 `abort`。只放弃活跃草稿，已保存批注和已发布版本保留。不要用临时脚本或目录递归删除代替这些命令。

已落实或保留待确认的处理结果不可覆盖；相同结果重发保留原处理轮次。待澄清的批注可以继续处理。新的修订意见另留批注，避免把历史处理记录改写成新结论。

回复用户改了什么，并提供原审阅地址和新版本号，用户可以在同一页继续下一轮。工具约束能防止常见覆盖和误清理；同权限 Agent 仍可能绕过 CLI 直接写文件，强制隔离需要宿主限制写入权限，不能把命令约定当作系统权限边界。

## 交付文档

交付目录优先采用用户指定的位置，其次沿用项目约定。默认使用业务项目根目录下的 `deliverables/<projectId>/v<revision>/`，与 `.document-review/` 审阅历史和技能安装目录分开。

选定一轮已发布版本，从同一个 `revisions/<revision>/` 原样复制 `flow.md` 和 `model.json`，也可从审阅页下载同版文件。用户要求一并交付的审阅线索等文件也放在交付目录。复制后核对两份副本与该版本的原件一致，再在聊天中链接交付目录里的文件，标明版本和未决事项。已有相同副本可直接复用，内容不同则保留现有文件并选用独立交付位置。用户只要流程说明时，仅交付 `flow.md`。

下游报告工具读取交付副本中的 `model.json`，将 HTML 等产物写到约定的输出位置。模型作为任务输入仅用于读取。需要修改业务内容时，回到原审阅任务通过 `draft → check → commit` 发布新版，再导出新版文件供下游使用。
