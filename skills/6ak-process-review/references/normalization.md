# 原始资料整理与判断

在首次整理原稿、业务内容变化或出现歧义时使用本页。字段与 JSON 表达以 [内容模型契约](model-contract.md) 为准。

## 业务背景与补充资料

从任务及项目提供的取材说明识别本次主原稿、术语与组织背景、适用的现行规范、评审线索和拟议改进。按本次角色、系统及流程范围读取相关章节。材料未注明用途时，依据正文判断；不确定且会改变业务结论时，保留待确认。

背景资料可以帮助理解术语、核对角色并发现遗漏。支持具体事实前，核对其适用范围、生效声明及版本关系，并把实际使用的原文纳入来源，引用具体行与原句。现行规范与原稿冲突时保留双方及业务影响。拟议控制措施可用于追问现状，写成现行步骤需要适用的生效依据或明确的用户补充。

只用来发现疑点的材料，可在复核备注记录用途。纳入模型的来源正文会随下游报告交付，选择与本次交付范围相关的资料。引用摘录时保留原文件与章节定位，不能把摘录行号冒充原文件行号。

## 从陈述到模型

1. 通读全部输入，列出业务范围、文档之间的引用、术语别名和明确的版本关系。把表格、备注、例外与正文一起处理；标题结构不是业务结构的保证。
2. 按“谁在什么条件下对什么对象做什么，产生什么结果”拆分可核对的陈述。没有说出的部分保留未知，不能为了填字段补写。
3. 跨平台、系统或地点整理同类业务时，先看操作方式。隐去名称，谁对哪类业务对象做什么、谁能决定或放行、做到哪一步才算完成？答案相同的部分在主流程写一次。可选做法可在同一动作中并列，如在商家后台单条修改或上传文件批改。若前一步选择通道、后一步提交，前者写选择依据，后者写具体操作。
4. 用主要事实与交接起草阅读分组，在交互审阅中确认分组后再展开全部事实与关系。分组、标题与节点摘要允许简练改写，但不能改变权限、条件、约束或适用范围。
5. 将每项重要事实连接到原文片段，并记录每段有效原文如何被纳入、合并或转为疑点。覆盖记录不替代复核：同一段可能包含多条独立要求。

## 节点划分

分组确认后，逐项读组内活动，依据触发、交接和结果决定哪些动作应在图上单独出现。

若某种做法改变风控边界（如事前拦截或留痕）、业务决定权（如谁有权定价）、操作对象或结果，在相应动作处写清适用条件及实际影响。有独立交接、不同去向或可单独确认的结果时，再据此拆节点或分支。例如，卖家改价后直接生效，与卖家仅能申报供货价、须等买手核定，即使用同一个后台，也要让读者看出谁决定哪一种价格。

- **连续步骤**。原文能说明前后依赖，且有责任交接或可单独确认的中间结果时，分别建节点并连接。例如申请已提交，下一位执行人据此办理。中间节点可以只有一个上游、一个下游；普通先后用顺序关系，额外的放行条件须有原文依据。
- **独立活动**。各有启动时点或事件、可以独立执行的巡检分别建节点，各记检查对象、周期和判据。重复运行同一项检查可以在节点内列出多个时点。只有材料说明如何交接、共同触发或流向同一下游时才连相应的边。仅知巡检存在时，可单列节点；去向缺失或证据冲突且影响处置时，保留待确认项。
- **同一活动**。完成一次判断所用的字段、计算和必须共同成立的约束留在同一活动。遇到长条件，回查是否混入调度、操作过程或其他活动，将这些内容归回对应节点。决定去向的复合判断完整保留在同一出口，即使图上需要折叠。标签长度不决定节点数。

## 结构化正文与逐字依据

整理链路是原始资料 → Agent 整理的 `model.json` → 流程图、节点列表与详情。列表正文取自节点字段所引用的 `claims.text`，并完整保留额外陈述、相关规则、关系和疑点；不是把 `sources.text` 的整行表格或报告 HTML 放进节点。后续人工修订和已采用补充也写入同一模型，不为不同视图维护另一份正文。

长表格的一格可能混合角色、系统路径、动作、约束和出口。先按含义拆为可核对的原子陈述，再分别归入 `role`、`system`、`trigger`、`input`、`actions`、`output`、`rules`；禁止把同一句包含多要素的复合长陈述重复挂进 `role`、`system`、`input` 等多个字段。`role` 与 `system` 优先写成简短可独立阅读的实体短语（如“各平台责任销售（L1）”“领星 ERP / 本地利润表.xlsx”），便于流程图卡片与详情顶栏直观呈现；具体操作和约束分别写入 `actions` 与 `rules`。每条陈述保留理解该要求所必需的对象、范围和条件。表头如 Who/Where 仅帮助理解，不作为业务正文照搬。

各入口名称、字段和文件格式可归入对应节点的系统、输入或规则，保留适用对象与逐字依据。同一节点已在触发条件或规则中列明适用对象时，动作直接写怎么做。某项操作只适用于其中一部分对象时，在该操作处点明。多个对象共用一句正文时，依据须覆盖所述范围。某处未提审批，审批要求仍属未知。影响执行的缺口和相互冲突的说法按下文保留。

`nodes[].title` 与 `claims.text` 沿用已确认的业务术语与自然表达，避免堆砌多个并列名词或照搬生硬的文档内部代号。具有业务含义的规则编号、代码标识、接口路径、文件名、比较符和单位应保留在对应规则、正文或依据中（例如 `rules[].title`、`/sale/floorPriceConfer`），不把 `[RULE-XXX]`、`ST-05` 等纯内部锚点编号硬塞进流程图节点标题。去掉纯排版的 `<br>`、表格分隔符、粗体标记及公式包装；清理发生在理解后生成陈述时，不改写来源正文或逐字证据，也不通过前端正则删字掩盖未整理的模型。

简短标题和卡片说明帮助定位，不能代替完整操作。节点 `actions` 写本步骤的执行或判断行为，决定下游分支的具体判定条件归入对应关系的 `conditionClaimIds`，避免把完整出口条件整句复述进上游 `actions` 造成重复阅读。拆分或改写后逐项核对否定、必须同时满足的条件、资格范围、阈值、分母、币种、时点及例外：例如“仅限已核验对象，某特区不适用”不能归纳成普遍免审。“未更新时次日催办”是条件行为，不能改成所有对象每日固定催办。输出字段只记录可依据原文确定的交付物，不把去向或整段操作复制为输出。

一段原文可以支持多条整理后陈述；各条证据仍逐字引用实际行段。跨章节补全规则时带入实际使用的来源。范围不一致、含义冲突或缺失的内容分别保留明示双方、推断理由或未知问题，不能为了让正文流畅而替用户做决定。审计整改计划和未来建议只供发现问题；没有现行适用依据或用户明确确认，不写成正在执行的规则。

## 关系的判断

对同一节点逐个列出“去向、走这条路所需的判断、原文”。把各出口的判断分别写入对应关系的 `conditionClaimIds`，尽量用一至两行能读完的完整短句，保留决定去向的对象、比较基准、阈值、单位、否定和组合条件。共用算法、操作和去向说明放在节点、规则或关系的其他陈述中。条件复杂时保留全义，图上可点开查看。每个条件可以引用同一行完整原文。

复核复杂分支时，用工作台“对照出口”一次核对同一起点的所有去向，特别检查同一目的节点是否有多种成立条件，以及仅在句末出现的否定或例外。图上的出口字母和组内节点号用于定位；业务先后、并行或回退分别由原文和关系表达。确认分组后可将便于对照的同层节点按阅读习惯依次列入模型。

例如同一行写“差异超过 2 件送复点，差异不超过 2 件归档”，两条边分别写“差异 > 2 件”和“差异 ≤ 2 件”，各自引用该行。复核时并排读各出口：互斥去向应能从条件区分；同一事件确实触发多个并行动作时可共用条件。仅说明异常出口时，不补写其反向出口；依据冲突且影响去向时保留双方原文与待确认项。

- 原文明示“完成 A 后 B”“A 通过才可 B”，可以表达对应先后或条件关系；条件与方向也必须有依据。
- “同时”“分别”“任一通道”需要区分并行、独立计划和备选路径，不能统一画成连续动作。
- 数据由 A 交给 B，不必然意味着所有 A 完成后所有 B 才启动。数据交付与控制顺序应按实际含义分别表达。
- Markdown 排序、表格行顺序、角色级别、行业常识和布局位置均不足以单独建立确定业务边。
- 跨分组关系仍须完整表达。没有依据的连接保留缺口；原文明示的回退、重复处理、异常出口不能为了画成单向图而删除。

## 推断、缺失与冲突

可接受的推断是有前提的整理，例如把“受理人”和“负责登记的同事”归为同一角色，但前提必须支持它们在本文确为同一对象。存在其他合理解释时标记歧义。

推断不能创造制度或操作事实，包括默认负责人、审批层级、阈值、SLA、系统接口、自动阻断与异常处置。解释原文含义不等于批准设计新流程。

冲突不是“选出最可信的一句话”。先检查是否范围、币种、分母、触发条件、时点或例外不同；确实无法兼容时，保留双方说法、定位和业务影响。仅凭文件修改时间或标题中的“新版”不能覆盖另一份材料；存在明确生效声明或用户确认时才据此处理，并保留处理依据。

对于缺失信息，区分：

- 原文未说明：显示未知；关键缺口建立问题。
- 原文明示不适用：保留“不适用”的明示依据。
- 多处说法冲突：双方均保留，不显示为一个确定值。

问题应具体到需要确认的事实，例如“处理满 48 小时时是否升级，从哪个动作开始计时”。当疑点影响解释但仍有其他部分可以确认时，继续交付可信的局部模型。

## 三个判断示例

### 散落的执行规则

原文写明“主管同意后再发布”和“编辑在发布后台操作”。

保留审核与发布两个动作，分别引用发布角色、系统和审批前提的依据。主管如何审批、拒绝后如何处理仍待确认。

### 两种数值口径

一份材料写明“受理后超过 48 小时未处理则升级”，另一份写明“上线前至少 48 小时提交变更”。

分开保留两条规则。第一条从受理开始计时，决定何时升级。第二条从上线时点倒计时，约束提交时间。

### 未说明先后

原文写明“每天检查值班记录。每周盘点备件”。

分别保留两个计划的周期。若需要判断日检是否影响周检，将关系标为待确认。
