# 原始资料整理与判断

在首次整理原稿、业务内容变化或出现歧义时使用本页。字段与 JSON 表达以 [内容模型契约](model-contract.md) 为准。

## 业务背景与补充资料

从任务及项目提供的取材说明识别本次主原稿、术语与组织背景、适用的现行规范、评审线索和拟议改进。按本次角色、系统及流程范围读取相关章节。材料未注明用途时，依据正文判断；不确定且会改变业务结论时，保留待确认。

背景资料可以帮助理解术语、核对角色并发现遗漏。支持具体事实前，核对其适用范围、生效声明及版本关系，并把实际使用的原文纳入来源，引用具体行与原句。现行规范与原稿冲突时保留双方及业务影响。拟议控制措施可用于追问现状，写成现行步骤需要适用的生效依据或明确的用户补充。

只用来发现疑点的材料，可在复核备注记录用途。纳入模型的来源正文会随下游报告交付，选择与本次交付范围相关的资料。引用摘录时保留原文件与章节定位，不能把摘录行号冒充原文件行号。

## 从陈述到模型

1. 通读全部输入，列出业务范围、文档之间的引用、术语别名和明确的版本关系。把表格、备注、例外与正文一起处理；标题结构不是业务结构的保证。
2. 按“谁在什么条件下对什么对象做什么，产生什么结果”拆分可核对的陈述。没有说出的部分保留未知，不能为了填字段补写。
3. 合并同义表达时同时检查对象、系统、时点、范围和业务效果。相同动作发生在不同通道、不同时间或不同审批边界时，通常应分别表达。
4. 先整理具体事实与关系，再归纳阅读分组。分组、标题与节点摘要允许简练改写，但不能改变权限、条件、约束或适用范围。
5. 将每项重要事实连接到原文片段，并记录每段有效原文如何被纳入、合并或转为疑点。覆盖记录不替代复核：同一段可能包含多条独立要求。

## 关系的判断

- 原文明示“完成 A 后 B”“A 通过才可 B”，可以表达对应先后或条件关系；条件与方向也必须有依据。
- “同时”“分别”“任一通道”需要区分并行、独立计划和备选路径，不能统一画成连续动作。
- 数据由 A 交给 B，不必然意味着所有 A 完成后所有 B 才启动。数据交付与控制顺序应按实际含义分别表达。
- Markdown 排序、表格行顺序、角色级别、行业常识和布局位置均不足以单独建立确定业务边。
- 跨分组关系仍须完整表达。没有依据的连接保留缺口；原文明示的回退、重复处理、异常出口不能为了画成单向图而删除。

## 推断、缺失与冲突

可接受的推断是有前提的整理，例如把“受理人”和“负责登记的同事”归为同一角色，但前提必须支持它们在本文确为同一对象。存在其他合理解释时标记歧义。

推断不能创造制度或操作事实，包括默认负责人、审批层级、阈值、SLA、系统接口、自动阻断与异常处置。解释原文含义不等于批准设计新流程。

冲突不是“选出最可信的一句话”。先检查是否范围、币种、分母、触发条件、时点或例外不同；确实无法兼容时，保留双方说法、定位和业务影响。仅凭文件修改时间或标题中的“新版”不能覆盖另一份材料；存在明确生效声明或用户确认时才据此处理，并保留处理依据。

对于缺失信息，区分：

- 原文未说明：显示未知；关键缺口建立问题。
- 原文明示不适用：保留“不适用”的明示依据。
- 多处说法冲突：双方均保留，不显示为一个确定值。

问题应具体到需要确认的事实，例如“处理满 48 小时时是否升级，从哪个动作开始计时”。当疑点影响解释但仍有其他部分可以确认时，继续交付可信的局部模型。

## 三个判断示例

### 散落的执行规则

原文写明“主管同意后再发布”和“编辑在发布后台操作”。

保留审核与发布两个动作，分别引用发布角色、系统和审批前提的依据。主管如何审批、拒绝后如何处理仍待确认。

### 两种数值口径

一份材料写明“受理后超过 48 小时未处理则升级”，另一份写明“上线前至少 48 小时提交变更”。

分开保留两条规则。第一条从受理开始计时，决定何时升级。第二条从上线时点倒计时，约束提交时间。

### 未说明先后

原文写明“每天检查值班记录。每周盘点备件”。

分别保留两个计划的周期。若需要判断日检是否影响周检，将关系标为待确认。
