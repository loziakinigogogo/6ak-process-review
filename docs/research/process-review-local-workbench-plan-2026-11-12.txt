基于 v0.1.3 的本地流程整理工作台改造方案
日期：2026-11-12
状态：设计方案，尚未实施；本文不构成开始开发、发布或更新业务项目安装副本的授权。
程序基线：v0.1.3，提交 7522168；当前研究分支另有复盘记录提交 8d600f8。

本次改造的目标是让不熟悉材料的用户借助流程图建立理解，直接调整节点及其关联内容，并在需要时请 LLM 协助。用户不必先读懂全部正文、确定问题类型或设计好修改方案。直接编辑、保存、重新打开和 Agent 修改后的即时可见，属于同一条基本使用流程。

本文将此前讨论收敛为实施设计。首个供用户试用的完整增量包括“看图 → 选节点 → 修改名称、详情与已有出口 → 保存 → 原位置更新 → 关闭重开恢复”。仅增加只读图不满足本次目标。

一、已确定的方案方向

1. 载体采用随 skill 安装、由固定命令启动或恢复的本地 Web 工作台。浏览器承担交互，Node 本地服务承担保存、版本协调和更新通知，业务项目保存任务数据。
2. 流程图是主要工作区域；完整正文、来源和疑点在选中对象后按需展开。图应帮助用户理解流转，不能要求用户先理解正文才能进入图。
3. 用户可以直接编辑，不以调用 LLM 为保存前提。LLM 承担解释材料、归纳内容、分析影响和协助重组。
4. 用户眼中的“节点”包括图上名称与摘要、点击后的详情、出口条件及去向；这些内容通过同一个编辑入口处理。
5. 图、详情、关系与文档来自同一份业务模型。展示设置、编辑缓存、待定改法和用户偏好另有明确归属，不塞进内容模型 v1。
6. 用户与 Agent 共用保存服务。Agent 可编辑工具提供的候选 model.json，由固定工具校验并应用；双方不直接覆盖同一个权威文件。
7. 保存工作草稿立即更新页面，正式发布版本另行形成。形成版本、用户核对、业务事实成立是不同含义。
8. 开发环境使用 Vite；安装包包含预构建前端和运行脚本。安装后的数据实时更新由本地服务推送，不要求每个业务任务重新安装前端依赖或执行构建。

二、v0.1.3 的可复用基础与实际缺口

已有基础：
- model.json 已表达 sources、claims、groups、nodes、relations、rules、issues 与 coverage；节点字段和关系条件具有稳定身份。
- process-review-view.cjs 已聚合节点正文、出口、条件和疑点，可以抽取为新工作台的内容投影基础。
- 现有页面支持步骤、句子和选文批注，真实批次保存、旧版定位、修改落点和历史查看。
- init、serve、draft、check、commit、status 等命令已有任务创建、受管修改与版本发布能力。
- 页面从 /api/review 读取数据，每四秒检查已发布版本。它能够在发布后更新，但看不到编辑中的草稿。
- 内容模型校验、来源核对、同版 flow.md 导出以及独立安装器可以继续复用。

需要新增或调整：
- 以图为主的工作界面，以及节点、关系、范围和原句的统一引用入口。
- 节点直接编辑、保存接口、未完成输入恢复、布局与整理偏好的持久化。
- 持续工作草稿，以及用户与 Agent 共用的写入协调。
- 保存后立即推送数据变化、保持位置与输入、解释具体变化。
- skill 的工作台启动与恢复入口，以及稳定的 Agent 内容工具。

重要限制：现有 draft/ 只允许 manifest.json、model.json、outcomes.json，并且最多绑定一个批次。它是受管发布事务，不能直接扩成包含任意 UI 文件的长期编辑目录。现有发布基线检查也不能替代对持续工作稿的并发保护。

三、用户如何使用工作台

首次进入：skill 读取任务和材料，生成或载入有依据的初稿，启动同一个工作台地址。已有任务恢复上次工作内容、整理偏好和可恢复的阅读位置。用户看到材料范围、主要动作与关系、相关未知；没有依据的部分保持缺口。

建议的桌面布局：

  顶部：任务名称、查找、保存状态、历史与导出入口
  主区：可读的流程图，包含分组入口、局部聚焦和完整图定位
  侧区：选中节点或关系的内容与编辑；来源、历史按需展开
  讨论：针对当前对象或选区的固定输入位置，显示可读引用标签

没有选中对象时，主区优先呈现图；侧区不常驻空表单。窄屏在图与编辑区之间切换，保留焦点与输入。第一版优先验证桌面使用，窄屏保证可读和可保存，不把完整手机图编辑列为已支持能力。

用户可以从“这里在做什么”“为什么走这条路”“审批在哪里”开始。提问允许没有选区，系统通过查找与必要澄清定位内容。明确的修改要求可以直接执行，不强制先经过问答。

典型直接编辑过程：
1. 点一个节点，看到它的名称、完整详情、入口背景和全部出口。
2. 修改名称或详情；修改条件并选择目标节点。页面给出本次变化预览。
3. 点保存。服务落盘成功后显示已保存，图和详情同步更新。
4. 切到其他节点、刷新或重开，已保存内容与保留的编辑稿仍在。

典型 LLM 协助过程：
1. 点节点、连线或选一片范围，也可直接提问。
2. 用户只写自然语言，程序附上版本、对象和必要上下文。
3. Agent 解释问题，或准备内容修改；可展示的小修改通过固定工具应用到工作稿。
4. 工作台在原位置显示变化及说明，用户继续直接编辑或追问。

四、图的呈现与完整节点编辑

4.1 图的内容规则

- 默认采用可读字号与明确的关注范围，支持分组视图、局部聚焦和完整图。完整图不强缩为一屏细小横条。
- 资料分组没有时序依据时标为“整理分组”；不固定四阶段，不根据标签顺序生成业务边。
- 保留 sequence、conditional、parallel、return、data、association 的实际类型。图例、文字或线型共同表达，不能只用颜色区分。
- 多入口、跨组出口、回路和不连通对象均可找到；不按入边数量自动宣布唯一业务起点或汇流等待规则。
- 图上节点以动作短名为主；关键条件、比较符、阈值与影响判断的未知不能被截断隐藏。长条件可在就近的出口列表完整显示，不能只靠悬停查看。
- 图上摘要须对应具体节点和陈述；更改相关正文后重新核对摘要。短名、详情和边标签之间的重复文字由投影生成，避免手工维护多份内容。
- 未确认内容仍能看到。确认进度不控制基本可见性，不采用“先确认才出现”的阅读前提。

4.2 一个节点编辑区的内容

图卡：节点名称，以及用户选定的角色、工具等可见字段。
详情：触发、输入、动作、输出、规则等内容，按有意义的段落呈现；保持对应 claim 身份。
入口：相关上游和进入条件，作为理解背景；编辑某条入口关系时明确定位该关系本身。
出口：逐条展示关系类型、完整条件、目标节点及相关疑点；一组出口可一起预览并保存。
依据：相关来源、明示／推断／未知和冲突，按需展开。

底层继续分别存 nodes、claims、relations 等集合。关系只保存一份，不复制为起点和终点各一份事实。保存节点编辑时，服务负责把表单映射为这些对象的一次一致更新。

首版图卡短名直接使用 nodes[].title，补充信息从已有关联字段投影；展示配置只决定显示哪些字段，不另存一份正文。需要重新概括时修改标题或相应陈述并保留依据，不通过截断长句制造摘要。

4.3 操作范围

首个完整试用版本提供：节点改名、既有详情项编辑、已有出口条件编辑与目标调整、移动阅读分组、节点位置调整、保存、取消当前输入、撤销最近一次已应用修改、精确引用。

后续结构编辑增量提供：新增和删除节点／连线、拆分和合并节点、重新分配原文归属。实施时逐项验收，不能用“支持节点编辑”概括尚未提供的功能。首版可由 Agent 协助完成明确的结构调整。

拆合必须交代原正文迁移、原 ID 与新 ID 的对应、出入连接和旧批注去向。用户只想调整表达粒度时，不能自动制造新的先后、职责或条件。

4.4 引用与偏好

节点点击、连线点击、多选／框选、段落／选文、无选区提问共用讨论入口。用户看到可读引用标签；系统携带稳定 ID、版本、原句和必要上下文。选择区域表示问题位置，不要求用户提前圈准完整修改影响范围。

任务偏好从具体反馈中记录：节点粒度、命名方式、图卡字段、分组视角、默认展开方式。记录适用范围及认可的例子，一次局部调整不自动变成全局规则。图上位置和折叠状态不成为业务依据，阈值、职责与流向仍按材料或明确用户补充处理。

五、数据保存与唯一权威工作内容

5.1 任务目录

沿用业务项目中的任务根目录，新增 workbench/，保留旧目录职责：

  .document-review/<任务编号>/
    task.json                         现有任务标识
    revisions/<正式版本>/             现有已发布快照，保持原格式
    batches/<批次>/batch.json          现有 v1 批注，保持原文与格式
    draft/                            现有发布事务，只保留原允许文件
    workbench/                        拟新增的持续工作区
      state.json                      当前权威工作状态
      buffers/<会话>/<对象>.json       未完成表单与输入缓存
      requests/<请求编号>/             新工作稿上的提问、意见和结果
      candidates/<候选编号>/           工具生成的 Agent 候选及基线记录
      transactions/<事务编号>/         变更、恢复与撤销记录

文件名和接口名均为拟定设计；实现时按同一契约维护，不允许各 Agent 为每个任务另造结构。所有任务数据归业务项目，不能写进安装技能目录，也不能当缓存整体清理。

5.2 state.json 的职责

外层使用独立版本的工作台协议，包含：
- workspaceSchemaVersion、taskId、stateRevision、workRevision、lastTransactionId；
- basePublishedRevision 与对应发布模型摘要；
- model：完整且严格符合内容模型 v1 的当前有效流程草稿；
- pendingEdits：尚未完成、尚未采用或性质待定的编辑记录；
- view：稳定布局、卡片展示及默认展开设置；
- preferences：有范围的本任务整理偏好；
- 已应用请求、变化说明和复核提示的引用。

state.model 是当前有效业务草稿的唯一权威。Agent 的候选 model.json 是基于某个版本准备的修改，正式 revisions 是历史；它们都不与当前工作稿独立演进。

pendingEdits 保存目标、基线、原值、输入值及未采用原因，不保存另一套可独立编辑的完整业务模型。页面可把这些内容叠加预览，但要在相应位置标明“待定／未采用”。暂定连线不伪装成模型已有的确定关系。

buffers 保存当前表单输入，并带对象 ID、原始文本和读取版本。停笔后自动保存编辑缓存，切换对象时也保存；服务失败时保留浏览器输入并提示未写入项目。缓存的更新不使正在处理业务内容的 Agent 候选无意义地过期。

stateRevision 在整个工作状态保存后递增，用于恢复与界面同步；workRevision 只在 model 或 pendingEdits 的逻辑变化后递增，用于内容引用与冲突检查。modelHash 按现有内容模型规则计算。布局、视口和编辑缓存变化不冒充业务版本。Agent 上下文同时记录相关整理偏好摘要，避免覆盖用户新明确的整理要求。

内容提交检查 workRevision、modelHash 和相关 preferenceHash。仅更新布局时，服务在最新状态上合并所声明的 view 字段，不以客户端旧的完整 state 替换当前状态；布局保存不递增 workRevision。buffers 使用自己的输入版本，拒绝较旧的异步保存覆盖较新的输入。

引用待定预览时还要携带 pendingEditId 和当时显示的文字，不能只引用未变化的有效模型。上下文工具返回相关待定编辑及其性质；Agent 不能因只读取 state.model 就遗漏用户已经保存的想法。候选应用只更新声明的模型对象及结果，保留最新的布局、偏好、缓存和其他待定编辑。

5.3 直接保存的含义

同一个保存入口承担三种明确结果：
1. 结构完整、性质明确的编辑写入 state.model，图与详情立即同步。
2. 未填完、引用目标尚缺或含义待定的内容写入 pendingEdits／buffers，显示“编辑稿已保存”；不要求等待 LLM 才能保存。
3. 写盘失败时保留输入并显示失败，不显示“已保存”，也不把仅在浏览器中的内容当成项目已保存数据。

已保存工作稿不等于正式发布，也不等于用户已经核对业务正确性。待定改法保留到下一次打开；正式导出明确是否还有未采用编辑，不把它们无声混入现状模型。

六、直接修改怎样保留事实、依据和影响

名称、分组、卡片字段等明确的表达调整由程序直接处理。节点字段按陈述项编辑，保留内容身份；自由输入无法可靠映射时先保存编辑稿，用户仍可继续写。

用户明确补充现行事实时，服务保存其原话为 user-feedback 来源及相应覆盖记录。新增或修订的陈述与该依据连接；共享事实有多处使用时，展示受影响位置，并区分只改此处与修改共享事实。只改此处可以拆出新的局部陈述，不能悄悄改掉其他节点。

修改事实时保留旧陈述与证据的可追溯关系。不能把“阈值 10”的原文直接作为“阈值 20”的支持证据。明确的纠正需记录采用理由；真实冲突保留双方和相应问题，未决问题不会因点保存自动解决。

用户提出未来方案或仍不确定时，先作为待定编辑保存并预览。origin=unknown 表示资料缺失，不能用它代替“用户提出方案”；explicit 也不表示业务已核实。当前任务意图不足以区分现状修订和方案时，只澄清这一处，输入照常保存。

已有条件可以直接编辑，不必再次让 LLM 从文字中猜出关联。服务校验对象、引用和一次保存的一致性；互斥、穷尽、计算基准和适用例外仍需语义核对。分支条件是文本及其引用，不冒充可执行规则引擎。

首版在修改后显示受影响内容与建议复核的具体原因，不新增逐节点确认操作。影响分析至少包括共享陈述、规则引用、关系条件、issue 与 premiseIds 依赖；不能只检查图上邻接。将来若引入确认状态，实际内容变化才触发相应失效，主动撤销一处确认不级联取消所有下游。

业务内容发生变化后，按现有规则重置 model.review 中不再适用的复核记录，并保留上一版记录。结构校验通过不能自动把 semantic 标为 passed；实际完成的语义与视觉复核范围分别记载。

七、统一保存、冲突与恢复

用户表单与 Agent 工具进入同一个保存服务；服务只接受当前任务的对象和明确操作。首版采用任务级串行写入及整个工作内容的版本／摘要检查，不承诺自动合并或复杂的细粒度锁。

一次逻辑保存按以下顺序完成：
1. 接收操作、读取基线和唯一请求编号。
2. 读取最新状态，检查基线、任务、目标身份和必要引用。
3. 在内存中形成完整的新状态，计算前后差异及待复核范围。
4. 写入可恢复的事务记录，完整写临时状态文件，再原子替换当前 state.json。
5. 落地可恢复回执，返回新的工作版本和变化对象，随后推送更新事件。

已应用的相同请求编号重试应返回原回执，不重复增加修改。若进程在替换状态后、回执完成前中断，根据 lastTransactionId 和事务摘要恢复，不能重复应用。撤销形成新的修改记录，不直接拿旧文件覆盖当前状态；后续又改过相关内容时先定位冲突。

Agent 读取 W12 后，用户把名称保存成 W13，Agent 对 W12 的整体候选不得覆盖 W13。首版保留候选，返回版本差异，Agent 重新读取后准备修改；用户输入仍保留。无冲突的正常保存不增加确认步骤。

编辑缓存采用会话／对象独立记录和自身基线。远端更新不覆盖正在输入的字段，用户保存时再核对其读取版本。断开服务时明确未写入项目，恢复后重试并检查版本。

发布事务、旧版命令适配和工作台写入共用协调机制。新版 CLI 在服务运行时通过服务提交；服务未启动时由固定入口启动或恢复后再操作。防止两个启动入口同时接管同一个任务。旧 0.1.3 程序不能认识新协调机制，不能宣称两个程序版本可以同时安全写同一任务。

八、保存与实时更新

开发环境：Vite 服务前端源代码与 HMR，Node 提供真实数据、保存和事件接口。图形组件和布局依赖在开发时安装并锁定版本，不由每个业务任务重新选型。

安装后运行：skill 带预构建前端，由 Node 提供静态资源、保存 API 和 SSE 数据更新流。运行所需资源与依赖均在技能目录内，路径相对技能目录解析；不依赖运行时 CDN 或开发仓库中的 node_modules。

数据更新路径：用户或 Agent 应用工作稿 → 服务落盘 → 推送任务／stateRevision／workRevision／modelHash／变化对象 → 前端按版本读取新数据 → 更新相关图卡、关系、详情和变化说明。

Agent 每完成一个可展示的小修改就调用一次固定应用工具，工具完成保存和推送，无需等待整批反馈结束或正式 commit。未通过解析或结构检查的候选保留在候选区，页面继续显示上一份有效工作稿，并提供失败说明。

前端需要保证：
- 名称或正文修改不重新排列整张图；结构变化只调整必要区域，并尊重用户固定的位置。
- 保留焦点、缩放、滚动、展开状态和输入；目标删除或拆分时显示身份变化，不跳到同名对象。
- 图与详情共同使用同一工作版本；异步旧响应不能覆盖新状态。
- SSE 重连后核对当前版本并补读最新状态，事件可重复或遗漏时仍能恢复一致。
- 新内容更新不自动表示用户认可；变化条目能定位具体前后内容及受影响原因。

建议以本机代表性复杂样本“保存成功后约 1 秒内看到变化”为初始体验目标，并在实现时实测记录，不把它写成已经达到的性能保证。

九、LLM 协助与反馈通路

用户直接编辑始终可用。LLM 协助分为解释、分析与内容修改，不因用户提出疑问就自动改变事实。

反馈上下文由工具组装：用户原话、问题对象、工作版本／摘要、精确选文、必要上下游、相关来源／规则／未知，以及适用的整理偏好。Agent 可按需继续读取材料。图上的问题范围、系统发现的影响范围和实际修改范围分别记录。

新工作稿引用拟使用 process-review-draft-ref:v1；新请求交接拟使用 process-review-draft-batch:v1。它们绑定工作稿版本、模型摘要、对象及原文快照，不把 workRevision 填入旧协议的发布 revision。对象被拆合、删除或改义后，按稳定身份与原快照处理。

requests 中持久保存用户当时看到的对象、原句、待定预览及必要上下文，或指向保证可恢复的事务快照。仅记录 W 编号、摘要和可变 state.json 路径不足以恢复旧意见。相应请求未处理完时，不能清理它依赖的快照和原话。

首个可试用版本使用真实的本地请求记录与当前对话交接：保存意见后，一键复制带上下文定位的短引用，用户发送到当前对话；Agent 通过固定工具领取和处理。网页显示“已保存／待发送”，复制不显示为已发送，也不声称自动唤醒模型。

纯解释请求只读取上下文并给出回答，不创建内容修改候选。首版回答可在当前对话阅读，Agent 同时通过固定 result 工具把解释、依据和对象引用写回原请求，工作台推送显示；这一回写不改变业务模型。这样即使发送仍需跨对话，用户也能在原问题处保留回答。

这条跨对话操作是明确的过渡限制。后续单独接入可实际调用 Agent 的运行入口，才开放在网页内直接发送、连续接收回复的完整对话过程。接入要验证实际调用、任务匹配、取消、错误回传和重复请求处理；HMR 或 SSE 不能代替这条调用通路。未具备宿主或模型调用能力时，继续使用诚实可用的短引用交接，不用更多状态按钮伪装已接通。

Agent 的固定内容流程：读取请求与上下文 → 获取带基线的候选 model.json → 修改业务内容和必要说明 → 调用 check/apply → 页面看到变化。工具生成候选目录、基线和回执；Agent 不为每批反馈写专用脚本，也不手改界面、布局程序或发布历史。

十、拟新增的程序入口与职责

对用户，skill 只需提供打开／恢复任务、继续整理和导出结果的稳定入口。以下命令和 API 是实施契约草案，当前尚不存在：

命令：
- workbench open：找到或建立任务，校验安装版本，启动或复用本地服务，返回地址和任务信息。
- workbench status/context：读取保存状态、指定对象及其依据与影响上下文。
- workbench request：读取指定新请求或兼容旧批次引用。
- workbench result：保存解释、澄清或处理说明，关联原请求；纯解释不改变业务模型。
- workbench candidate：生成受管候选与基线；不覆盖已有候选。
- workbench check/apply：校验候选并经统一保存入口应用到工作稿，返回实际差异。
- workbench publish/export：冻结工作版本并生成正式快照、同版 flow.md 和交付副本。

本地 API：
- GET /api/workbench/state 与 /context：读取当前工作状态或指定对象的聚合内容。
- POST /api/workbench/edits：提交直接编辑或候选应用，包含基线和幂等请求编号。
- PUT /api/workbench/buffers：保存未完成输入，不把缓存当成已采用业务内容。
- POST /api/workbench/requests：保存用户问题和修改要求。
- POST /api/workbench/results：保存 Agent 回答或处理说明，关联请求与引用对象。
- GET /api/workbench/events：SSE 通知工作版本及保存状态变化。
- POST /api/workbench/publish：从明确工作版本形成正式版本。

服务保持本机访问及现有来源检查原则；写入口按任务和对象处理，不接收浏览器提供的任意磁盘写入路径。浏览器状态、候选目录与业务模型的权威关系由存储层统一维护。

职责边界：
- skill：规定启动恢复、材料定位、内容处理和工具调用流程；装配所需脚本、资源与说明。
- Web 前端：绘图、编辑、引用、预览、保存状态、差异与位置保持。
- Node 服务和固定工具：持久化、版本协调、上下文提取、结构检查、恢复、推送和导出。
- LLM：解释资料、形成有依据的流程表达、理解偏好、处理歧义、分析并修订内容。
- 用户：直接修改或表达想法，确定自己的整理偏好，对重要业务结论和最终结果作判断。

十一、正式发布、旧任务与协议兼容

1. model 子对象继续使用内容模型 v1。新工作版本、布局、待定改法、确认状态与候选元数据使用外层工作台协议。
2. 旧任务首次打开时，从最新已发布版本创建工作状态，不改写 revisions、batches 或原稿。没有节点的有效模型显示范围与问题，不生成虚构流程。
3. 旧 draft/ 已存在时，保留并展示恢复入口。先完成、明确放弃或通过显式导入保留旧候选；不能在初始化时清理或覆盖它。
4. 新工作台发布冻结的 state.model 时，通过现有发布校验与快照能力生成正式版本。旧 draft/ 若被适配器使用，仍只含原三类文件。日常保存不等待这一步。
5. 新工作稿请求的处理结果保存在 workbench/，记录应用工作版本和正式发布版本；它们不伪装成旧 batches 中的已处理结果。发布记录只关联该次冻结快照中实际包含的改动；请求已被后续撤销时不标为已发布落实。
6. 对 pricing-ref:v1、pricing-review-batch:v1，继续按原发布快照与原摘要解析。旧批次接入时保留原话、原目标和原轮次；首版正式发布最多结算一个旧批次，沿用旧事务对完整 outcomes 的约束，其余批次保持待处理。不能把新请求或其他批次结果混进旧草稿。
   结算时适配器用指定旧批次创建原三文件事务，填入冻结工作模型和该批次全部 outcomes。其他批次的内容即使已被当前模型包含，也保留其尚未结算的状态；后续依据真实应用记录核对，不凭文本相似自动宣布已处理。
7. 旧 batch 当前已无变化需要落地时，按原接口填写有依据的 noChangeReason；不能为了凑 changeTargets 修改无关内容。新工作台的一轮发布包含哪些人工与 Agent 改动，需在发布预览中完整显示。
8. 自定义审阅分组的旧任务继续保留旧阅读入口。图从真实模型构建，不从旧页面标题、序号和段落邻接反推关系。
9. 形成版本时核查工作版本和发布基线；失败保留全部工作状态。发布期间短暂串行化内容应用，浏览器仍可输入并保存缓存。发布成功后将 state 的 basePublishedRevision、基线摘要及 model.report.version 一起推进，并递增工作版本、推送更新；pendingEdits 和 buffers 原样保留其基线，重新应用时核对差异。flow.md 从正式模型生成，不能手工维护第二份正文。工作稿版本不冒充 report.version。
   正式快照与工作状态推进使用同一发布事务标识。若快照已落地而 state 尚未推进，重启时从回执恢复推进，不重复发布，不丢弃期间保留的输入；若已出现额外内容修改或外部发布，保留双方状态并定位冲突，不以旧冻结模型覆盖新工作稿。
10. 待定编辑可以继续保留；导出应说明存在未采用内容。用户可选择只交付当前有效模型，不能静默把待定方案混入现状。
11. 回退至 0.1.3 后，旧程序仍能读取兼容的已发布 v1 内容与旧批次；未发布工作台内容由新版恢复，不能声称旧版能编辑它。禁止两个版本并发写同一任务；外部发布变化必须使当前工作基线失效并保留差异。
12. 新迁移／备份工具要纳入 workbench/。只迁移旧 revisions 和 batches 不能宣称完成整项任务迁移。恢复记录、未解决意见和任务历史不可随临时运行文件一起清理。

十二、实现范围与分阶段交付

以下为未来开发安排。本轮只保存方案，不创建前端工程、安装依赖、修改代码、迁移任务或执行发布。

阶段 A：基础运行与存储
建立 Vite 开发环境、预构建资源打包、Node 保存服务、持续工作状态、候选应用、版本检查、编辑缓存和恢复。复用现有模型校验与任务定位。该阶段是内部基础，不作为用户需求已完成的交付。

阶段 B：首个完整试用版本
提供可读流转图、统一节点编辑、名称／详情／已有出口条件和去向编辑、分组与位置调整、直接保存、撤销、原位更新与重开恢复。直接编辑已有共享内容时具备最小影响说明和保护，明确的任务偏好可以保存并随上下文提供给 Agent。同时接通新工作稿引用、真实对话交接、解释结果回写和 Agent 应用后的差异。用一条完整流程让用户试用，而非交付孤立的只读图。

阶段 C：结构编辑与偏好延续
逐项补齐新增／删除节点和连线、拆分／合并、正文归属迁移，以及跨节点重组时的影响分析和偏好应用。每项结构操作同时验证旧引用、依据、未知和冲突的表达。

阶段 D：网页内 Agent 调用与发布收敛
在运行入口确实可用时接入网页直接发送、连续回复和取消。完成旧任务／批次兼容、迁移回退和独立安装验证后，再发布技能版本。若该调用能力不可用，保留阶段 B 的可用交接方式并明确能力边界。

拟修改的代码职责：
- skills/6ak-process-review/SKILL.md：把交互工作台纳入工具职责，固定运行和内容修改流程；静态报告可继续作为单独导出。
- skills/6ak-process-review/scripts/：新增工作台入口、存储、上下文和发布适配模块；现有工具按需抽取共享函数。
- skills/6ak-process-review/assets/workbench/：新前端源与预构建资源；旧 grouped-review 页面保留兼容入口。
- skills/6ak-process-review/references/：工作台数据、直接编辑、来源与引用协议说明。
- scripts/pack.cjs、scripts/install*.cjs、package.json：未来按需增加构建清单与安装验证；用户运行不依赖仓库源码环境。
- .qa/：隔离任务、浏览器证据和实际验证记录。

图编辑组件与布局库需要用长条件、多入口、回路和稳定位置的样本验证后锁定具体版本；选型不改变本方案的内容模型、保存和交接契约。首版不引入云端账号、多人跨机器实时协作或新的确认进度系统。

十三、验收标准

技术验收：
T1. 无 LLM 调用时，用户可修改节点名称、详情和两个出口，保存后图与详情一致，重启服务后仍存在。
T2. 未写完的正文、缺少目标的暂定连线可以持久保存；待定预览与有效业务模型清晰区分，导出不混入未采用内容。
T3. 切节点、关闭编辑区、刷新、重开均保留已落盘编辑稿；写盘失败不能显示保存成功，恢复后可重试。
T4. 两个入口同时修改、Agent 旧候选与用户新修改相遇时不丢内容；冲突定位明确，重试不重复应用。
T5. 在临时写入、状态替换、回执生成等位置模拟中断，恢复后只有完整旧状态或完整新状态，历史不缺失。
T6. 修改图卡、正文、关系、来源、规则或推断前提后，差异与复核原因能够定位；未决问题不被无声解决。
T7. 数据推送断线、重复事件和异步乱序不会留下图文不同版；改文字不重排全图，输入和当前焦点保持。
T8. 共享句子局部修改、批量出口非法末项、节点拆合和撤销，不产生悬空引用、部分写入或错误证据归属。
T9. 旧 v1 引用、旧批次、旧任务、已有 draft、自定义审阅分组和回退场景按兼容方案处理。
T10. 独立安装到隔离项目后可打开、编辑、保存、恢复和导出；安装目录不混入任务数据，运行无需开发仓库和 CDN。

理解与协作验收：
- 让不熟悉资料的使用者借助图、详情、来源和提问理解一个实际片段。允许使用这些帮助，记录哪些帮助有效、哪里仍困惑，不要求用户事先知道流程或按钮。
- 保留完整复杂背景，再缩小操作任务；覆盖一处分支和一次跨组／回路场景，避免重新用孤立小例子掩盖整体困难。
- 观察用户能否直接指向不理解的位置，表达缺失内容，修改一个完整节点，并看懂变化；同时记录误把分组当时序、数据关系当执行顺序、汇流当等待规则的情况。
- 至少完成一轮真实自然语言反馈：既有明确修改，也有指代不清或仍不确定的意见；核对实际引用、材料解释、变更范围和结果。固定 QA 写回不能代替这项验证。
- 用一处用户认可的节点划分或命名作为例子，检查下一轮同类内容是否沿用，并保留合理例外。

开发验证使用隔离的合成任务，覆盖复盘中的长文本、多个入口、分支、汇流、回路与跨组复杂度，结果保存在 .qa/。真实资料试用另行记录来源、授权范围和实际覆盖，不把测试补充写回业务任务。

修改技能和运行脚本后执行 npm test，并补足与改动相符的存储、接口、浏览器及独立安装检查。涉及整理规则时，按 evals/procedure.md 分开记录结构、语义、反馈和泛化验证。本文没有新增已通过测试或用户认可的结论。

十四、版本与方案边界

本次仅形成方案，package.json 保持 0.1.3，技能源、安装器和业务项目安装副本不变。

未来满足验收后递增发布版本；业务项目仍通过独立安装器选择版本手动更新。若工作台外层协议或旧协议适配发生变化，随发布提供明确迁移与恢复说明；内容模型 v1 和旧引用不能靠改名假装兼容。
