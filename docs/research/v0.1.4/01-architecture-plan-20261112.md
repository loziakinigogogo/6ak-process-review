# 基于 v0.1.3 的本地流程整理工作台改造方案

> [!IMPORTANT]
> **状态：⭐️ 生效中核心设计基准 (ACTIVE DESIGN BASELINE)**  
> **产生日期**：2026-11-12  
> **程序基线**：v0.1.3，提交 `7522168`  
> **定位**：0.1.4 本地流程工作台总架构设计蓝图。确立了“以图为主、节点直接编辑、用户与 Agent 共用保存服务、复制短引用回对话”的现代架构基座。

---

## 本次改造目标

让不熟悉材料的用户借助流程图建立理解，直接调整节点及其关联内容，并在需要时请 LLM 协助。用户不必先读懂全部正文、确定问题类型或设计好修改方案。直接编辑、保存、重新打开和 Agent 修改后的即时可见，属于同一条基本使用流程。

首个供用户试用的完整增量包括**“看图 → 选节点 → 修改名称、详情与已有出口 → 保存 → 原位置更新 → 关闭重开恢复”**。仅增加只读图不满足本次目标。

---

## 一、已确定的方案方向

1. **载体采用随 skill 安装、由固定命令启动或恢复的本地 Web 工作台**。浏览器承担交互，Node 本地服务承担保存、版本协调和更新通知，业务项目保存任务数据。
2. **流程图是主要工作区域**；完整正文、来源和疑点在选中对象后按需展开。图应帮助用户理解流转，不能要求用户先理解正文才能进入图。
3. **用户可以直接编辑，不以调用 LLM 为保存前提**。LLM 承担解释材料、归纳内容、分析影响和协助重组。
4. **用户眼中的“节点”包括图上名称与摘要、点击后的详情、出口条件及去向**；这些内容通过同一个编辑入口处理。
5. **图、详情、关系与文档来自同一份业务模型**。展示设置、编辑缓存、待定改法和用户偏好另有明确归属，不塞进内容模型 v1。
6. **用户与 Agent 共用保存服务**。Agent 可编辑工具提供的候选 `model.json`，由固定工具校验并应用；双方不直接覆盖同一个权威文件。
7. **保存工作草稿立即更新页面，正式发布版本另行形成**。形成版本、用户核对、业务事实成立是不同含义。
8. **开发环境使用 Vite；安装包包含预构建前端和运行脚本**。安装后的数据实时更新由本地服务推送，不要求每个业务任务重新安装前端依赖或执行构建。

## 二、v0.1.3 的可复用基础与实际缺口

### 已有基础
* `model.json` 已表达 sources、claims、groups、nodes、relations、rules、issues 与 coverage；节点字段和关系条件具有稳定身份。
* `process-review-view.cjs` 已聚合节点正文、出口、条件和疑点，可以抽取为新工作台的内容投影基础。
* 现有页面支持步骤、句子和选文批注，真实批次保存、旧版定位、修改落点和历史查看。
* `init`、`serve`、`draft`、`check`、`commit`、`status` 等命令已有任务创建、受管修改与版本发布能力。
* 页面从 `/api/review` 读取数据，每四秒检查已发布版本。它能够在发布后更新，但看不到编辑中的草稿。
* 内容模型校验、来源核对、同版 `flow.md` 导出以及独立安装器可以继续复用。

### 需要新增或调整
* 以图为主的工作界面，以及节点、关系、范围和原句的统一引用入口。
* 节点直接编辑、保存接口、未完成输入恢复、布局与整理偏好的持久化。
* 持续工作草稿，以及用户与 Agent 共用的写入协调。
* 保存后立即推送数据变化、保持位置与输入、解释具体变化。
* skill 的工作台启动与恢复入口，以及稳定的 Agent 内容工具。

> [!WARNING]
> 现有 `draft/` 只允许 `manifest.json`、`model.json`、`outcomes.json`，并且最多绑定一个批次。它是受管发布事务，不能直接扩成包含任意 UI 文件的长期编辑目录。现有发布基线检查也不能替代对持续工作稿的并发保护。

## 三、用户如何使用工作台

### 首次进入
skill 读取任务和材料，生成或载入有依据的初稿，启动同一个工作台地址。已有任务恢复上次工作内容、整理偏好和可恢复的阅读位置。用户看到材料范围、主要动作与关系、相关未知；没有依据的部分保持缺口。

### 桌面三栏布局
* **顶部**：任务名称、查找、保存状态、历史与导出入口
* **主区**：可读的流程图，包含分组入口、局部聚焦和完整图定位
* **侧区**：选中节点或关系的内容与编辑；来源、历史按需展开
* **讨论**：针对当前对象或选区的固定输入位置，显示可读引用标签

> 没有选中对象时，主区优先呈现图；侧区不常驻空表单。窄屏在图与编辑区之间切换，保留焦点与输入。第一版优先验证桌面使用。

### 典型直接编辑过程
1. 点一个节点，看到它的名称、完整详情、入口背景和全部出口。
2. 修改名称或详情；修改条件并选择目标节点。页面给出本次变化预览。
3. 点保存。服务落盘成功后显示已保存，图和详情同步更新。
4. 切到其他节点、刷新或重开，已保存内容与保留的编辑稿仍在。

### 典型 LLM 协助过程
1. 点节点、连线或选一片范围，也可直接提问。
2. 用户只写自然语言，程序附上版本、对象和必要上下文。
3. Agent 解释问题，或准备内容修改；可展示的小修改通过固定工具应用到工作稿。
4. 工作台在原位置显示变化及说明，用户继续直接编辑或追问。

## 四、图的呈现与完整节点编辑

### 4.1 图的内容规则
* 默认采用可读字号与明确的关注范围，支持分组视图、局部聚焦和完整图。完整图不强缩为一屏细小横条。
* 资料分组没有时序依据时标为“整理分组”；不固定四阶段，不根据标签顺序生成业务边。
* 保留 `sequence`、`conditional`、`parallel`、`return`、`data`、`association` 的实际类型。图例、文字或线型共同表达，不能只用颜色区分。
* 多入口、跨组出口、回路和不连通对象均可找到；不按入边数量自动宣布唯一业务起点或汇流等待规则。
* 图上节点以动作短名为主；关键条件、比较符、阈值与影响判断的未知不能被截断隐藏。长条件可在就近的出口列表完整显示，不能只靠悬停查看。
* 图上摘要须对应具体节点和陈述；更改相关正文后重新核对摘要。短名、详情和边标签之间的重复文字由投影生成，避免手工维护多份内容。
* 未确认内容仍能看到。确认进度不控制基本可见性，不采用“先确认才出现”的阅读前提。

### 4.2 节点编辑区内容
* **图卡**：节点名称，以及用户选定的角色、工具等可见字段。
* **详情**：触发、输入、动作、输出、规则等内容，按有意义的段落呈现；保持对应 claim 身份。
* **入口**：相关上游和进入条件，作为理解背景；编辑某条入口关系时明确定位该关系本身。
* **出口**：逐条展示关系类型、完整条件、目标节点及相关疑点；一组出口可一起预览并保存。
* **依据**：相关来源、明示／推断／未知和冲突，按需展开。

## 五、数据保存与唯一权威工作内容

### 5.1 任务目录结构
沿用业务项目中的任务根目录，新增 `workbench/`，保留旧目录职责：

```text
.document-review/<任务编号>/
  task.json                         现有任务标识
  revisions/<正式版本>/             现有已发布快照，保持原格式
  batches/<批次>/batch.json          现有 v1 批注，保持原文与格式
  draft/                            现有发布事务，只保留原允许文件
  workbench/                        拟新增的持续工作区
    state.json                      当前权威工作状态
    buffers/<会话>/<对象>.json       未完成表单与输入缓存
    requests/<请求编号>/             新工作稿上的提问、意见和结果
    candidates/<候选编号>/           工具生成的 Agent 候选及基线记录
    transactions/<事务编号>/         变更、恢复与撤销记录
```

### 5.2 state.json 的职责
外层使用独立版本的工作台协议，包含：
* `workspaceSchemaVersion`、`taskId`、`stateRevision`、`workRevision`、`lastTransactionId`；
* `basePublishedRevision` 与对应发布模型摘要；
* `model`：完整且严格符合内容模型 v1 的当前有效流程草稿；
* `pendingEdits`：尚未完成、尚未采用或性质待定的编辑记录；
* `view`：稳定布局、卡片展示及默认展开设置；
* `preferences`：有范围的本任务整理偏好；
* 已应用请求、变化说明和复核提示的引用。

`state.model` 是当前有效业务草稿的唯一权威。Agent 的候选 `model.json` 是基于某个版本准备的修改，正式 `revisions` 是历史；它们都不与当前工作稿独立演进。

### 5.3 直接保存的含义
同一个保存入口承担三种明确结果：
1. 结构完整、性质明确的编辑写入 `state.model`，图与详情立即同步。
2. 未填完、引用目标尚缺或含义待定的内容写入 `pendingEdits` / `buffers`，显示“编辑稿已保存”；不要求等待 LLM 才能保存。
3. 写盘失败时保留输入并显示失败，不显示“已保存”，也不把仅在浏览器中的内容当成项目已保存数据。

## 六、直接修改怎样保留事实、依据和影响

* 名称、分组、卡片字段等明确的表达调整由程序直接处理。节点字段按陈述项编辑，保留内容身份。
* 用户明确补充现行事实时，服务保存其原话为 `user-feedback` 来源及相应覆盖记录。新增或修订的陈述与该依据连接；共享事实有多处使用时，展示受影响位置。
* 修改事实时保留旧陈述与证据的可追溯关系。不能把“阈值 10”的原文直接作为“阈值 20”的支持证据。
* 用户提出未来方案或仍不确定时，先作为待定编辑保存并预览。`origin=unknown` 表示资料缺失，不能用它代替“用户提出方案”。
* 已有条件可以直接编辑，不必再次让 LLM 从文字中猜出关联。服务校验对象、引用和一次保存的一致性。
* 业务内容发生变化后，按现有规则重置 `model.review` 中不再适用的复核记录，并保留上一版记录。

## 七、统一保存、冲突与恢复

用户表单与 Agent 工具进入同一个保存服务；服务只接受当前任务的对象和明确操作。首版采用任务级串行写入及整个工作内容的版本／摘要检查。

一次逻辑保存按以下顺序完成：
1. 接收操作、读取基线和唯一请求编号。
2. 读取最新状态，检查基线、任务、目标身份和必要引用。
3. 在内存中形成完整的新状态，计算前后差异及待复核范围。
4. 写入可恢复的事务记录，完整写临时状态文件，再原子替换当前 `state.json`。
5. 落地可恢复回执，返回新的工作版本和变化对象，随后推送更新事件。

## 八、保存与实时更新

* **开发环境**：Vite 服务前端源代码与 HMR，Node 提供真实数据、保存和事件接口。
* **安装后运行**：skill 带预构建前端，由 Node 提供静态资源、保存 API 和 SSE 数据更新流。
* **数据更新路径**：用户或 Agent 应用工作稿 → 服务落盘 → 推送任务／`stateRevision`／`workRevision`／`modelHash`／变化对象 → 前端按版本读取新数据 → 更新相关图卡、关系、详情和变化说明。
* **体验目标**：本机代表性复杂样本保存成功后约 1 秒内看到变化。

---

## 九、LLM 协助与反馈通路

* 首个可试用版本使用真实的本地请求记录与当前对话交接：保存意见后，一键复制带上下文定位的短引用，用户发送到当前对话；Agent 通过固定工具领取和处理。
* 纯解释请求只读取上下文并给出回答，不创建内容修改候选。
* Agent 固定内容流程：读取请求与上下文 → 获取带基线的候选 `model.json` → 修改业务内容和必要说明 → 调用 check/apply → 页面看到变化。

## 十、技术验收标准摘要

* **T1**：无 LLM 调用时，用户可修改节点名称、详情和出口，保存后图与详情一致，重启服务后仍存在。
* **T2**：未写完的正文、缺少目标的暂定连线可以持久保存为待定编辑；导出不混入未采用内容。
* **T3**：切节点、关闭编辑区、刷新、重开均保留已落盘编辑稿；写盘失败不能显示保存成功。
* **T4**：两个入口同时修改、Agent 旧候选与用户新修改相遇时不丢内容；冲突定位明确。
* **T5**：在写入中断模拟中，恢复后保持一致事务，历史不缺失。
* **T7**：改文字不重排全图，输入和当前焦点保持。
* **T10**：独立安装到隔离项目后可打开、编辑、保存、恢复和导出。
