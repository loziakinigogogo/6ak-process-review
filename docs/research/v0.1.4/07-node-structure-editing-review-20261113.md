初评日期为 2026-11-13。2026-11-15 实现首版后，按使用反馈调整结构编辑的分工和入口。

## 11 月 15 日使用反馈后的方案

结构调整从右侧抽屉的「交给 Agent」发起，入口旁显示当前节点或选中的 `A → C`。用户点选预设，先核对一条可编辑的任务，然后把完整交接复制到现有 Agent 对话。Agent 查阅引用、原文和相关上下游，给出候选差异。用户核对业务含义并确认应用，再回工作台查看结果或订正文案。下文的首版初稿及验收记录保留了手动结构表单的历史。

| 意图 | 交互与提交范围 |
| --- | --- |
| 起草新节点 | 从现有资料和用户说明整理一项活动。可以单独提交节点。连线在有明确依据时列为独立变更，若关系待确认则保留问题。明确要求在所选顺序线补一步时，再核对前后两段及受影响字段。 |
| 调整连线 | 从画布或「完成后走向」选中具体关系。交接带上已有两端节点供参考，核对类型、条件和交付内容。涉及改接时，从最新工作稿读取新端点，核对新旧端点受到的实际影响。确需联动的节点字段与连线改动分别列入候选，供用户逐项核对。 |
| 拆分或补充 | 将三条原有预设放到「交给 Agent」中。可以附上未保存文字或先前的结构草稿，作为需要核对的输入。 |
| 订正文案 | 详情先用于阅读。点「修订文案」可修改标题、已有文字和已有条件的表述。分组、关系类型和去向通过图和详情核对。 |

### 交接预览

预设按抽屉的当前对象填好任务，用户可直接采用或修改这一段话。处理对象单列，端点节点、划选的原句和主动附上的未保存草稿显示在参考材料。起草独立节点时，当前节点或连线供查证。没指定对象时，在使用 skill 的 Agent 对话中直接说明任务，例如「从原文找漏掉的步骤」。按当前对话唯一定位的任务读取最新工作稿，有多份可能时先问是哪一份。正式审阅任务和独立工作台分别按自己的任务路径、基线和候选流程处理。

例如，用户划中审批卡里的「通过后提交档案管理员」，可以预览并复制「核对审批和归档是否需要拆成两个节点，把候选连线和异常退回问题分别列出」。当前审批卡可以作为处理对象，划选原句及附上的草稿供 Agent 核对。遇到确实会影响方案的业务事实，再在原对话中澄清。

「确认并复制」将任务、处理范围、参考材料与版本化引用一起交接。候选的确认、应用和撤销沿用下文的版本和事务约束。仅创建节点时，新增前后关系集合应完全一致。调整连线时，候选要单列线的改动及实际受影响的节点字段。

首次将结构调整移入 Agent 入口时，曾在隔离浏览器中验证桌面和窄屏上的节点和连线引用、文案订正及旧草稿交接。专项回归使用合成候选，验证独立新增节点、后续接线、版本检查和撤销。文案保存会保留已经存为待定的旧结构建议。那一轮的日志和截图见 `.qa/workbench-agent-first-FBrhu8/`。

## 11 月 15 日首版初稿

工作台提供直接编辑和 Agent 辅助两条路径。用户已明确内容、条件和接法时，在工作台新增或调整节点。需要重读原文、重新分配内容或核对关系时，在现有「复制引用」处选择预设，把指令和引用粘贴到能读取该任务的 Agent 对话。首版在对话中核对候选差异，确认后调用现有写入服务，返回工作台继续编辑。后文保留 11 月 13 日独立评审，首版分工及提交流程以本节为准。

### 直接编辑的范围

| 用户要做什么 | 首版行为 |
| --- | --- |
| 改名称、操作说明、职责、输入或产出，调整已有出口 | 沿用当前右栏编辑。修改涉及共享陈述或推断依赖时，保留输入，提示核对关联影响。 |
| 新增节点、建立或改接关系 | 首版补齐的手动能力。由用户填写自己已经确认的内容、端点、关系类型和所需条件，预览后保存。 |
| 在顺序线上补一步 | 在选中的无条件顺序线 `A → C` 上预览 `A → N → C`，只替换该路径。新增活动写在 N，若交付者、接收方或启动条件随之变化，可一起修订 A、C 的对应字段。若要把 A 已有活动移到 N，沿用已经填写的草稿，按连续拆分核对其内容与旧线。 |

垂直拆分也可能得到 `A → N → C`，其中 N 承接从 A 拆出的已有活动。水平扩展可得到 `A1 → C`、`A2 → C`，两路可以按条件择一、分别交付或满足明确的汇合条件。水平和垂直描述的是结构，具体业务含义来自原文或用户确认。按拆法生成可预览的旧线映射，只追问归属或条件未明的关系。预览列出实际受影响的上下游字段，例如 C 的「收到谁的结果才开始」，经用户确认随结构一起保存。

### 三条可复制的 Agent 指令

每条指令都附带所选节点或关系的版本化引用，用户可以追加已知事实或缩小范围。共同要求是基于引用核对当前任务，给出候选修改、逐项依据和待确认事项，等待用户确认后再应用。

1. **按条件或渠道拆分**

   > 核对原文和我的补充，判断这个节点是否合写了不同条件或渠道下的活动。提出如何分别成卡，说明哪些动作共用、各路何时适用、现有入线和出口如何分配、各自交付什么。若都连向同一下游，请核对下游何时启动。条件边界、覆盖范围或汇合规则缺少依据时，列出具体待确认事项。

2. **拆成连续步骤**

   > 将原节点已经描述的活动拆为有依据的前后步骤，标出各步承接的操作、职责、输入和结果，以及支持业务先后的原文。核对每条旧入线和出口的归属，尤其是失败返回和数据交付。若先后或归属未明，保留为待确认。

3. **从原文补充节点信息**

   > 回查本任务原文，包括当前节点尚未引用的相关段落。找出遗漏的职责、触发、输入、操作、产出或规则，基于当前工作稿列出字段级增删改及出处。保留用户已有修改，原文与用户修订冲突时并列展示。没有新依据时说明检索结果。需要整卡重写时，也先给出逐项差异供确认。

### 候选的确认、应用与撤销

1. **交接。** 沿用 `process-review-workbench-ref:v1` 的任务、对象和工作版本。引用本身对应已保存快照。用户可以明确附上未保存文字，标为独立草稿并保留原输入。Agent 核对任务与版本，发现引用已过期时，先回看当前工作稿和受影响对象。
2. **生成候选。** Agent 在 `candidate` 提供的模型文件中起草，保留原来源、对象身份和未决问题。检查目标节点的全部入线、出线和共享陈述依赖，对话中展示实际改动及需要决策的关系。列出文字和连线前后差异、旧线是保留／改接／拆为多条、受影响的上下游字段，以及原文出处、用户补充、推断依据和待确认问题。原稿有冲突时保留双方陈述。
3. **确认。** 应用授权针对已展示的候选编号、基线和差异。用户可以只认可图形组织，或明确要求应用候选。需补充业务事实时，记录具体陈述及其来源。影响本次提交有效性的未知项随有关调整留待确认。与本次改动无关的未知和冲突可继续保留。用户若只想先应用明确的部分，先把互相依赖的改动留在同一批，单独展示依据充分、应用后自洽的候选，再确认该批。
4. **应用。** Agent 对已确认的候选调用 `apply`，从确认到应用使用同一份候选内容。工具核对当前工作版本、模型摘要及候选记录的偏好基线，校验模型，再将节点、陈述、关系和相关上下游修订作为一次内容事务保存。生成或审核期间只要工作版本发生变化，即使是无关节点的修改，也保留旧候选和当前输入，基于最新工作稿生成候选，展示新差异并重新确认。已手动建立的同一活动按节点 ID、职责和上下游衔接核对后复用。
5. **撤销。** 候选尚未应用时可关闭或留作待定。应用后，工作台的「撤销最近一次内容修改」在该候选仍为最新内容事务时，生成一个恢复应用前内容的新工作版本，包含相关上下游的文字和连线。保留后来独立的布局操作、引用快照和未提交输入。已有后续内容提交时，按原候选的前后差异和当前工作稿生成反向候选，保留后续独立修改，列出重叠或依赖冲突，再由用户确认。当前快捷撤销按最近一次内容事务操作。

首版在对话中确认用户授权。工具用 `review-candidate` 返回差异、证据与 `reviewHash`，`apply --confirm` 核对该摘要和基线。结构表单在同一浏览器和地址下可恢复，引用仍指向已保存快照。继续使用内容模型 v1、已有任务目录和既有引用协议。[工作台说明](../../../workbench/README.md#agent-内容工具) · [内容模型](../../../skills/6ak-process-review/references/model-contract.md)

### 场景提问与解答

三个 GPT-6 Astra 子代理分别就分支和汇合、手动插入和连续拆分、原文补充和版本事务提问，由其他三个子代理解答。以下六例使用合成资料，列出首版验收预期。

#### 1. 两路报修各自交付

原文说平台告警与热线报修各自核对设备编号并交付有效记录。调度收到一份有效记录即可处理，同一故障的重复记录并入已有工单。用户要将合写的 A 拆成两张卡。**两路都接到建单节点 C 时，去重细则未知会阻止拆分吗？**

候选将旧 `A ─数据交付→ C` 映射为两条分别有出处的数据线，保留 C 已有的通用触发条件。任一路都可交付，两路也可同时发生。去重判据和合单责任人继续待定。用户说「这个图可以」时，只记录他认可图形组织，需要实际应用时确认所见候选。

#### 2. 检修时长决定额外复核

原文说预计停机 `≤ 4 小时` 做班组自检，`> 4 小时` 加做安全复核，全部适用检查通过后才复运。所有检修先登记，拆机后可修改预计时长。现有 `登记 → 检查 → 复运`，检查失败返回返修。**用户希望两路共用自检，并先应用确定的部分。补充「用拆机后的最新时长」后，整次拆分能否提交？**

先提一个可独立应用的文字候选，补充已知阈值、自检为共用活动和复运门槛。保留登记顺序及原有检查失败返回关系。用户补充若明确描述现行事实，则保留原话作为来源。按这项补充，从 3 小时调到 6 小时的工单需增加安全复核。已完成自检如何处理、两项检查的先后及返修后需重做什么仍待确认，影响这些规则的分支及返回线留在结构草稿里。

#### 3. 把已有的签发操作移到插入节点

A「检测及出具报告」已有检测、录入、签发三项，接 C「通知委托方」，另向 D 归档检测记录与正式报告。原文只明确授权签字人复核签发、客服收到正式报告后通知。用户点 A 到 C 的线新增 N「复核签发」，随后想从 A 迁出签发。**能否沿用插入入口，并让 A 到 D 的旧数据线原样生效？**

保留已填的 N 草稿，按连续拆分同时预览 A、N、C 的字段和 A 到 D 的两类交付。原文支持 C「收到正式报告后」，交付人需单独核实。若有依据表明 A 仍转送正式报告，可保留该交付。若旧线的这部分只依赖拆前合写的节点，先保留待定，避免提交签发已迁出、正式报告交付归属却未经核对的结构。用户可以另行确认并应用有独立依据的 C 字段修正。

#### 4. Agent 生成期间，用户手动新增了同一步

W8 的 A 合写审核和提交退款，审核失败返回 B 补件。用户发出连续拆分指令，并附未确认的「提交前由组长复核大额退款」。等待期间，他手动在 A 与财务 C 之间新增 N「提交退款申请」，保存成 W9。**此时如何采用拆分意图，又保留手动新增和未应用草稿？**

基于 W9 核对 N 的节点 ID、实际活动及端点，确认是同一步后复用 N 和已有连线。新候选展示提交操作从 A 迁到 N、A 到 B 的失败返回仍属于审核，以及 C 的启动文字是否需要更新。组长复核原句保留在未应用草稿，大额阈值和适用渠道继续待定。「其他能定的先保存」用于缩小范围，应用前仍展示并确认新候选。整次撤销恢复 W9 的内容，保留此前已手动提交的 N。

#### 5. 原文补充已确认，应用前出现新工作版本

W12 保留「维修员检查后出报告」与用户已保存的班长复核修订。Agent 从一段尚未被节点引用的原文中找到设备编号和测量记录两项附件要求。用户确认只应用附件要求，另附的紧急维修文字继续作为未保存草稿。应用前用户又把报告名称改为「设备维修记录」，保存成 W13。**旧确认能直接用于旧候选吗？若 W13 只改了无关节点呢？**

两种 W13 都触发任务级基线检查。保留旧候选，以 W13 重建只涉及附件要求的候选。保留新名称或无关改动、两种职责来源、未解决的职责冲突和其他未知，以及未提交的紧急维修草稿。再次展示从 W13 出发的差异，说明附件变化是否与此前一致，经确认后应用。

#### 6. 撤销原文补充，保留布局与后续修订

W20 存在客服审核与仓库核验职责的冲突。用户确认候选，应用后以事务 T21 新增仓库回传实收数量的操作、到财务的数据线及财务接收说明。随后只拖动卡片，并继续编辑未提交的破损件说明。**现在撤销应恢复什么？如果后来还提交了独立的职责修订 T22，怎么只撤 T21？**

T21 仍为最新内容事务时，整次撤回两处节点文字和数据线，原有材料与职责冲突保留，布局、引用快照和破损件草稿也保留。继续提交草稿前核对撤销产生的新基线。若已有 T22，快捷撤销会选中 T22。要只撤 T21，基于当前稿提出反向候选，撤回当次对来源的采用，保留已登记的来源与 T22，标出依赖或重叠冲突后再确认。

## 11 月 13 日独立评审

本次讨论关注一个问题：用户打开工作台，看到一个想重新组织的节点时，能否从眼前的界面自然地迈出第一步，并在不臆造业务关系的前提下完成调整。

建议首版把 **“拆成两个节点…”直接放在右栏“操作说明”标题旁**。用户点中想调整的节点，就能开始重新组织内容；不必先选中某条操作，也不必先保存文字。第二个入口是顺序线上的 **“在这两步之间新增一步…”**。两者共用草稿、预览和保存机制，但需要不同的业务默认值。

## 讨论背景与约束

当前用户可以看着画布，在右栏修改节点名称、已有操作说明和部分既有出口。有时用户希望把一个节点中的业务内容重新组织成多个节点，并自行在工作台完成。

此前考虑过“从某条操作移到新节点”和“拆出一步”：前者假设现有文字已经切得合适，后者没有解释新节点在流程中的位置，以及已有连线如何处理。

以“收集调价需求与底价”为例，右栏有“同步协议底价与最高折扣范围”和“全品类运营接收全量底价”两项操作，原节点有一条数据交付线通往“测算售价、供货价与配额”。用户可能只想改写两项操作，也可能想把其中一项单独成卡。仅凭文字，无法判断两卡之间是否要连线，也无法确定原数据交付线应从哪张卡发出。

本次先做只读分析，不修改代码或任务数据。方案沿用内容模型 v1、已有任务目录及 `pricing-ref:v1`、`pricing-review-batch:v1` 引用兼容要求。后续若实施，技能修改仍在本仓库维护源进行；验证使用隔离合成任务，结果保存 `.qa/`，实际跨领域验证范围按技能评估程序记录。

## 八个使用场景

除第 1、6、7 项引用当前调价节点外，其余是用于检验交互的假设场景，不代表当前业务事实。

| 场景与用户原话 | 预期结果 | 涉及的上下游关系 | 仍缺什么判断 |
| --- | --- | --- | --- |
| **1．只改文字**。右栏有两条操作：“把最高 Discount 的说法写清楚，事情还是这些。” | 在原输入框改写，保留一张卡。 | 节点及全部连线不变。 | 是解释术语，还是改变折扣规则？后者需要新增依据。 |
| **2．合写内容拆成前后两步**。选中“核对资料并提交审批”：“核对完才能提交，把这张卡分开。” | 核对、提交分别成卡。 | 上游→核对→提交→审批；其他出口逐条核对。 | 原出口是否都属于提交阶段？失败返回是否仍发生在核对阶段？ |
| **3．既有顺序中补缺失步骤**。画布已经是“准备资料→提交审批”：“中间漏了核对，补上，两张卡原文不用动。” | 新增核对卡。 | 仅将选中的顺序线替换为准备→核对→提交。 | 核对是否确实位于这条路径，是否存在绕过它的情形？ |
| **4．条件分支**。一张卡合写校验与主管复核：“超出阈值才交主管，其余直接继续。” | 判断与复核分开；形成条件出口。 | 判断→复核或原下游；复核后还需明确去向。 | 阈值、等号归属、条件是否覆盖所有情况，以及在哪里判定。 |
| **5．并行后汇合**。一张卡写运营检查、财务检查：“两边同时做，都通过才能发布。” | 两张检查卡及明确汇合条件。 | 同时发起两路，满足汇合条件后发布。 | 等全部还是任一路？失败、超时怎么办？两条入线本身不能表达这些答案。 |
| **6．关系尚不明确**。调价节点右栏：“全品类运营接收全量底价单独成卡，但它和另一项什么关系还没核实。” | 先形成两卡内容方案，保留待确认问题。 | 不自动生成两卡间的线，也不自动迁移通往测算的数据线。 | 是否有先后？谁向测算交付？两卡是否代表不同渠道？ |
| **7．拆分同时改写**。右栏已经输入未保存文字：“原文切法不合适，我要重新写成两步，名称也一起改。” | 在同一草稿中重写、分配内容、改名，一次保存。 | 按重写后的业务含义重新核对所有相关连接。 | 新文字是否超出原证据；职责、输入、结果和规则分别适用哪张卡。 |
| **8．多个既有出口**。原卡有正常继续、失败返回、数据交付三个出口：“发送单独出去，校验失败还是在原卡退回。” | 原卡保留校验，新卡承担发送。 | 返回线留原卡；正常路径接新卡；数据线单独决定起点。 | 条件在哪里判断、数据在哪里产生，是否实际需要新增或复制一条关系。 |

**场景 2、3 是关键对照组。**用户都会说“加一个核对步骤”，但前者重组已有内容，后者补充原来缺失的活动。两者不能都执行“新增卡，然后把原出口挪过去”。

## 当前 demo 的能力边界

### 画布与右栏

画布支持选中、查看、移动，尚无结构编辑入口。点击连线会打开源节点，并定位右栏对应出口；手拉建线和 Delete 删除被禁用。这个现有定位行为可以承接“在线上插入”的入口。依据：[main.tsx 第 596 行](../../../workbench/frontend/src/main.tsx#L596)。

右栏适合改已有内容。名称、分组、已有操作和其他已有字段可编辑；“操作说明”仅遍历已有陈述，没有增加、拆分或删除操作的控件。依据：[main.tsx 第 614 行](../../../workbench/frontend/src/main.tsx#L614)、[第 617 行](../../../workbench/frontend/src/main.tsx#L617)。

### 完成后走向

“完成后走向”实际包含所有出边，既包括顺序、条件，也包括数据交付等；可改已有目标和条件文字，不能新增出口或修改关系起点、类型。这个标题容易让人把数据交付理解成执行顺序。依据：[草稿收集全部出边，第 52 行](../../../workbench/frontend/src/main.tsx#L52)、[关系编辑区，第 620 行](../../../workbench/frontend/src/main.tsx#L620)。

### 保存与恢复

当前已有三种不同的保存／恢复语义：

- 编辑缓冲用于保留输入，浏览器缓存作为补充。
- “保存节点”提交内容或待定建议；“还原输入”恢复当前已保存工作稿。
- “撤销最近一次内容修改”另走内容撤销，布局整理还有独立撤销。

结构编辑应延续这些区别。依据：[输入缓冲，第 228 行](../../../workbench/frontend/src/main.tsx#L228)、[还原与保存，第 478 行](../../../workbench/frontend/src/main.tsx#L478)、[内容撤销，第 541 行](../../../workbench/frontend/src/main.tsx#L541)。

## 入口比较与首版选择

| 候选入口 | 用户第一步点哪里 | 何时决定业务关系 | 评价与首版取舍 |
| --- | --- | --- | --- |
| **右栏“拆成两个节点…”** | 选中节点后，点“操作说明”标题旁按钮。 | 可以先重组内容；应用前确认两卡关系和旧连线归属。 | **主入口。**贴合当前视线位置，也覆盖关系未明和拆分改写。 |
| 节点菜单中的“拆分” | 打开画布卡片菜单。 | 同上。 | 可作为重复入口；当前卡片没有菜单，不值得只为此先建菜单体系。 |
| **顺序线上的“插入一步”** | 点线，右栏对应出口出现“在 A 与 C 之间新增一步…”。 | 点击时已经指定插入位置；预览时核对新增活动和替换的线。 | **第二入口。**首版限无条件顺序线。 |
| 分组里的“新增节点” | 在分组导航或画布空白处新增。 | 新卡出现后，还要找上游、下游和内容来源。 | 适合补独立活动，但不能自然解决“眼前这张卡合写了”的问题，暂缓。 |
| 右栏“新增分支” | 在关系区新增条件出口。 | 必须填写条件、目标、后续及判断位置。 | 适合场景 4；需要分支编辑能力，首版先保留为待定方案。 |
| 某条操作旁“移到新节点” | 点具体操作。 | 容易让用户误以为移动文字就完成了结构调整。 | 只能作为拆分编辑器内的快捷操作，不作为唯一入口。 |

两条推荐路径都应允许带着未保存文字进入。**“先保存文字，再回来改结构”不应成为必经步骤。**

节点拆分和边上插入可以共用结构草稿、预览、连接清单、一次提交及撤销，但不能共用无差别的动作语义。插入针对一条已经确认的顺序关系，拆分针对一个已有内容容器；内容分配和原关系归属是拆分时必须补上的决定。

## 主路径 从节点开始拆分

### 第一步 从眼前节点开始

右栏“操作说明”旁常显“拆成两个节点…”。点击后，右栏进入拆分编辑，画布保留原卡位置，旁边出现带“预览／新增”标记的新卡。提示“当前输入已带入，尚未应用到流程”。

### 第二步 整理两张卡的内容

右栏提供“原节点”和“新节点”两个可切换的内容区，均可修改名称和操作。原名称作为初值保留，新名称由用户填写。支持整条移动，也支持两边自由改写、增加内容条目，不能要求先选一条原句。

“输入、职责与完成结果”继续可展开，并提示尚未分配的内容。原卡上的职责、规则、输入等不能自动复制到新卡，避免扩大适用范围。

### 第三步 明确两卡关系并核对现有连接

关系选择不预选，提供四种选项：

1. 原节点完成后做新节点。
2. 新节点完成后做原节点。
3. 已确认两卡不直接连接。
4. 尚不确定／需要其他结构。

前三种可以继续核对并应用；最后一种可以保存待定方案。“不直接连接”不等于并行，也不表示已经确认汇合规则。

将本区命名为 **“现有连接”**，逐条列出关系类型、条件、原起点和终点。出口选择“仍从原节点发出／改从新节点发出／待确认”；入线也列出并核对目标。检查范围来自整个模型，包含组外关系。初始保持原线仅是预览起点，保存前必须确认其适用性。需要复制关系、改变类型或复杂汇合的情况，首版保存待定方案。

### 第四步 画布和右栏共同预览

画布标明“新增卡”“新增连接”“改接”，右栏用实际名称列出变更清单；可以来回调整。新卡默认同组、就近放置，不触发整图重排。

不宜仅用虚线表示草稿，因为现有虚线已经用于数据、返回和关联关系。依据：[graph-routing.tsx 第 48 行](../../../workbench/frontend/src/graph-routing.tsx#L48)。

### 第五步 一次保存

底部按钮变成“取消拆分”和“保存这次调整”。名称、内容分配、关系决策完整时，一次提交原卡文字、新卡、相关连线和问题关联。仍有关系待确认时，明确显示“保存待定方案”，有效流程保持原结构。

保存期间冻结本次结构表单，失败后恢复编辑并保留全部输入；基线冲突时重新核对受影响内容和连接，不能自动覆盖新版。

### 第六步 区分取消和撤销

“取消拆分”恢复进入拆分前的文字草稿，包括此前尚未保存的输入。切换节点或刷新则保留结构草稿，回来继续。

保存成功后，保持局部视口并高亮两卡；一次内容撤销恢复保存前的完整模型。若还要继续原来的未保存文字，应从保留的入口草稿恢复。布局撤销仍独立，后续手动移动不随内容撤销一起丢失。

### 默认值与明确确认的边界

可以直接采用的默认值是：原卡保留 ID、新卡获得新 ID、同整理分组、保留原证据、带入当前输入、原卡位置不动。

**业务先后、出口起点、入线目标，以及职责和规则是否同时适用于两卡，都需要用户确认。**文字条目的先后排列、画布左右位置、同属一个分组，都不构成业务顺序的证据。

## 第二路径 在既有顺序中插入

1. 点击一条**无条件 `sequence` 线**，右栏定位该出口并显示“在 A 与 C 之间新增一步…”。
2. 填写新节点 N，立即预览 `A → N → C`。
3. 原 A、C 的内容不因插入自动搬迁，A 的其他出口保持原样。若来源节点已有未保存文字，带入本次草稿并列入保存摘要；其他节点的独立草稿不随之提交。
4. 取消恢复进入前状态；保存和撤销复用整次结构事务。

这里可以默认替换所选顺序线，是因为用户已经明确选择“在这两步之间插入”。节点拆分没有这个前提。数据交付、条件、返回或并行线首版不提供这种快捷插入；点到它们时显示关系类型，并允许回到源节点开始拆分。

## 调价节点完整实例

### 当前已知状态

原卡 `pricing-demand` 没有入线，包含两项操作，唯一出边 `demand-to-price` 是数据交付，通往“测算售价、供货价与配额”。对应关系陈述是“销售接收调价要求或市场洞察后启动算价”。它没有证明全品类运营接收必须发生在同步之后，也没有证明数据应由拆后的第二张卡交付。

依据：冻结模型的[操作陈述，第 75 行](../../../.qa/workbench-fixtures/pricing-knowledge-base-20261113/model.json#L75)、[关系依据，第 1674 行](../../../.qa/workbench-fixtures/pricing-knowledge-base-20261113/model.json#L1674)、[数据关系，第 3739 行](../../../.qa/workbench-fixtures/pricing-knowledge-base-20261113/model.json#L3739)。

### 开始拆分

用户点击“拆成两个节点…”后，可以：

- 将原卡暂命名为“同步协议底价与折扣范围”，保留第一项操作。
- 将新卡命名为“接收全量底价”，放入第二项操作。
- 同时改写两边文字，核对原来的职责、触发、完成结果和规则。
- 在连接区看到“数据交付：原节点 → 测算售价、供货价与配额”，选择其归属。

如果用户此时只确认“想单独展示”，选择“尚不确定”，就保存两卡待定方案，并留下两个明确问题：**两项活动如何衔接；哪张卡向测算交付什么。**有效图不变。

### 获得业务确认后的不同结果

假设用户随后明确补充：“这两步确实依次执行，接收完成后由接收环节向测算交付”，才可预览以下结构。**这是交互演示的假设补充，不是本次已核实的业务事实。**

```text
同步协议底价与折扣范围 ──顺序──→ 接收全量底价
                                      │
                                   数据交付
                                      ↓
                         测算售价、供货价与配额
```

这项补充必须作为本次用户确认来源保存。若用户确认的是“两条独立渠道”，则不生成两卡间顺序线，并继续单独判断数据出口；不能套用上面的图。

## 内容模型与旧任务兼容

**内容模型 v1 不需要升级。**首版只增加工作台操作与草稿格式，保持已有模型和任务目录可读。

### 陈述和证据

纯移动陈述时，保留 claim ID、origin、evidence、推断依据，调整节点 `claimIds` 和 fields。未说明的字段继续为空，不填默认职责。

改写或一条拆成多条时，新建用户修订陈述，保留旧陈述和原文；记录旧陈述到新陈述的对应关系。现有文字保存已经采用新增用户来源的做法，可抽取复用，见 [workbench-store.cjs 第 422 行](../../../workbench/scripts/workbench-store.cjs#L422)。

新增或改接关系时，需要支持新端点、新方向的依据。原整卡的数据交付证据不能直接充当“新卡负责交付”的证明；用户同意分卡也不等于确认业务顺序。

### 未知和冲突

保留 open issue，按含义关联原卡、新卡或两者；拆分不自动解决问题。冲突双方的明示陈述都保留。v1 已明确禁止用 unknown 陈述建立确定关系。

依据：[model-contract.md 第 18 行](../../../skills/6ak-process-review/references/model-contract.md#L18)、[关系及问题约束，第 29 行](../../../skills/6ak-process-review/references/model-contract.md#L29)。

### 工作台格式扩展

拆分映射、入口草稿和结构决策放操作记录及独立结构草稿命名空间，不往 v1 节点随意增加 `splitFrom` 等字段。旧任务缺省没有结构草稿，无需迁移；旧节点缓冲继续按原格式读取，未知结构草稿版本应保留并提示。

## 首版验收场景

实施验证使用隔离合成任务，结果保存 `.qa`。以下为待实施的验收要求，不是本次已完成测试。

1. **入口与纯文字编辑**：点中节点后，无需打开菜单或滚动即可找到“拆成两个节点…”。只改两条操作并保存时，节点数量、关系数量和端点完全不变。
2. **未保存文字、取消与整次撤销**：先输入未保存改写，再进入拆分；取消后原输入逐字保留。完成拆分时一次保存落地全部变化，一次撤销恢复原模型；失败和版本冲突均不丢草稿。
3. **插入与拆分区分**：对无条件顺序线插入，只替换所选路径，其他出口不动；对实际 `demand-to-price` 数据线，不出现直接串行插入动作。
4. **多出口逐条确认**：准备正常、失败返回、数据交付三个出口。拆分时必须逐条有处理结果；存在“待确认”就只能保存待定方案，失败返回不会自动迁移到新卡。
5. **未知、证据和引用保真**：关系未明时可保存两卡方案并刷新恢复，有效图保持原样。确认应用后，纯移动陈述保留身份，改写有独立来源，未知与冲突仍可见，拆分前引用仍指向原版本含义。
