## 1. 用户提出的新方向

用户认为，0.1.3 的文本流可以理解为把流程图节点放进列表／表格，各种额外内容挂在节点下面，因此具有脑图或树状内容结构的特征。

据此提出：

- 在“流程图模式”的页面上，沿用当前以展示为主的流程图风格，支持非重型编辑。
- 深入编辑时进入“脑图模式”，更方便在节点下面挂载不同种类的内容。
- 附属内容不固定，因此其组织方式需要比固定字段表单更灵活。

这一方向承接 10 的查阅／编辑双形态定位，也为深度编辑提出了专门视图。此前 A／B／C 的编辑容器位置仍可作为局部交互参考，不应继续作为整体架构的首要选择。

## 2. 前一段讨论揭示的内容录入问题

开放手动编辑后，用户可能补充原稿中没有的内容。若要求先把补充写入另一份文档，再让 LLM 提取并挂回节点，会使简单提醒也变成繁重流程。

助手建议：**允许直接在图上或节点内容中创作；这次输入本身可以成为可追溯的内容记录。** LLM 可协助整理和检查关联，不必成为每段文字进入工作台的必经入口。

| 操作示例 | 建议处理 |
| --- | --- |
| 缩短标题、润色卡片短说明 | 作为展示表达修订；注意不要悄悄改变原意或覆盖完整说明 |
| 添加“这里容易漏填币种，请留意” | 直接挂为用户提醒，保留作者、所属对象和修改记录 |
| 补充“这个环节实际上由财务负责” | 作为用户明确补充的现行事实，关联本次输入并更新相关内容 |
| 添加“建议以后增加财务复核” | 保留改进建议身份，与当前已采用流程区分 |

内容性质不能只由栏目名称决定。“注意：金额超过一万元必须主管审批”虽然放在注意事项下，仍表达业务规则，可能影响条件、连线和审批节点。可以轻量录入，但不能因此认为相关流程已自动同步。

以上是交互原则，不代表现有 v1 已支持任意形式的自由内容。用户提醒、业务事实和改进建议的存储方式仍需设计；不能把全部手写备注一概转成已核实的业务事实。

## 3. 建议的总体分工

**流程图表达业务流转，内容树组织内容归属。** 两者围绕同一批节点工作。

| 区域／视图 | 主要用途 | 建议承担的编辑 |
| --- | --- | --- |
| 流程图视图 | 看整体结构、上下游及实际展示效果 | 标题、执行者、短说明、已有条件文字等轻编辑；直接添加简短提醒；调整布局 |
| 节点内容视图 | 深入整理节点及附属内容 | 增补长说明、组织栏目与层级、调整内容顺序，整理注意、例外、资料和建议 |
| 右侧详情 | 查阅当前节点的完整内容 | 保持稳定的阅读用途；是否保留少量就地修订入口另行决定，不承载全部编辑表单 |
| 固定便签 | 跨节点对照少量内容 | 主动固定、调整摆放、回到原内容；不另建一份独立正文 |

与查阅／编辑形态的关系建议为：

- **查阅形态**：以流程图和右侧完整详情为主，减少编辑控件。
- **编辑形态**：提供“流程图／节点内容”切换，图上轻编辑，内容树中深入整理。

不需要为此立即建立四套独立页面或四份状态。内容树是否也向纯查阅场景开放，可后续再判断。

## 4. 内容树的结构：少量固定核心＋可扩展内容

节点仍有明确的卡片核心：行动／事件标题、执行主体、简短说明；分组色标与简单组内编号辅助定位。详细内容允许按实际需要增加和组织，不要求每个节点具有相同栏目。

以下仅为结构示意，不是新增业务事实或确定的数据 schema：

```text
测算目标售价
├─ 执行者：平台责任销售
├─ 卡片短说明
├─ 完整操作
│  ├─ 核算基础费用
│  └─ 记录测算结果
├─ 注意事项
│  └─ 部分地区存在附加运费
├─ 平台差异                 ← 用户按需要增加
│  ├─ 平台 A
│  └─ 平台 B
└─ 待确认
   └─ 附加费是否已包含在运费表中？
```

用户可直接增加“平台差异”等栏目，并在下面写内容。界面不必要求用户先判断应该塞进哪一个预设业务字段；来源与内容性质可在相应条目上呈现，避免每次录入都要求填写一套证据表单。

“脑图”准确表达了层级与归属的想法，但不一定要实现成横向展开的卡片画布。长说明在此类画布中容易占据大量空间。助手倾向先定义为**节点内容树／内容视图**，采用树形组织和可展开正文；最终偏脑图还是偏大纲的视觉形态尚未确定。

## 5. 不能混淆内容层级与业务结构

流程存在分支、汇合、回路和共享节点，不能把业务图强行转成单父节点的树。

- 内容树的父子关系表示“这段内容属于谁”，不自动表示业务先后、子流程或执行依赖。
- 在内容树中排序或拖动段落，只改变阅读组织，不自动改流程顺序和连线。
- 一个节点被多条路径经过时，仍是同一个节点；不要按每条路径复制一份可独立修改的正文。
- 跨节点共用的规则应关联同一份内容；节点详情可呈现引用，避免多份副本漂移。
- 已有业务关系作为带类型、条件和去向的关联呈现，不能以内容树的缩进替代。
- 增删流程节点、拆分、改接等结构编辑的手动范围仍待讨论；此次方向不构成全手动结构编辑的定案，现有 Agent 候选流程继续作为设计基线。

## 6. 两个视图必须保持同源与连续

从图上切到内容树，直接定位当前节点；从内容树返回图，恢复原分组、选中对象和视口。必要时也应定位到对应的段落或字段，减少重新寻找内容。

两种视图共用稳定身份和内容记录，修改应反映到相应展示处。切视图不丢未提交输入；草稿、当前采用内容和待定建议仍须区分。右侧详情不能在用户不知情时把草稿当成有效正文。

卡片摘要与完整操作的关系仍是待定问题：摘要能否单独编辑、底层内容更新后如何提示或重新归纳，需要继续设计。此文没有把“允许手动新增内容”推导成“摘要可以与正文无约束地独立变化”。

## 7. Draft／report 与依据的关系

助手建议将其理解为连续的整理、完善和呈现过程：从原稿产生初稿，用户直接补充和修订，再以流程图及详情供查阅或输出。

报告可以包含后来由用户补充的内容，不要求每句话都出现在最初那批原稿中。需要如实区分：原稿陈述、用户补充、整理推断、提醒、建议以及未决问题。记录来源不等于完成事实核实，保存内容也不等于采用建议。

未知和冲突不会因进入自由内容树而消失；提出未来做法的文字也不能自动进入现行流程。轻量录入与准确表达内容性质应同时成立。

## 8. 实现前仍需讨论的边界

1. **内容视图形态**：可折叠大纲、空间脑图，还是两者结合；用长说明实际比较可读性与编辑成本。
2. **自由内容的最小单位**：段落、条目或区块；允许的嵌套层级，以及必要的内容性质如何表达。
3. **摘要编辑策略**：独立润色、从正文生成及两者同步如何配合。
4. **轻编辑范围**：图上哪些修改直接完成，哪些引导到内容视图；如何明确内容组织与流程结构编辑的区别。
5. **模型兼容**：内容模型 v1 对字段有严格约束。不能直接把任意树形栏目或摘要字段加入既有 `nodes/fields` 并宣称兼容；需明确投影、版本化扩展或迁移方案，保留稳定 ID、已有任务与 `pricing-ref:v1`、`pricing-review-batch:v1` 等引用。

主会话可先用一个同时含短说明、长操作、注意事项、自定义栏目、共享规则和未决问题的节点，讨论“图上修改一句—进入内容树增加一段—返回图查看”的完整体验，再决定具体页面布局。
