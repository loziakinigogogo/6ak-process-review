## 二、最初要解决的真实问题

1. 用户需要把散乱业务资料整理成可核对、可修改的流程。旧工具保留了正文、来源、句子级批注和版本反馈，但文字密集、确认项琐碎、多层 drawer 使主干难以辨认。
2. 用户最初发现的通常是“这一片流程不合理”，未必能先判断应该拆分、合并、改连接还是改分支。若要求先选择正确操作，工具就在要求用户提前完成流程设计。
3. 需要同时看懂整体结构和实际动作文字。只提供图，节点含义会丢失；只提供文字，复杂分支与汇流又要求用户在脑中自行建图。
4. 审阅不同于执行业务：互斥分支也要全部核对；汇流节点只维护一次审阅状态；回路不能造成无限审阅。

## 三、研究路线与变化原因

### 1. 逐节点审阅
* **做法**：默认打开起点，展示完整角色、触发、输入、动作、产出和局部前后关系；选句批注、核对修改、确认或跳过，再选择分支继续。
* **收益**：正文完整，批注对象明确，原句与依据容易保留。
* **暴露的问题**：真实复杂流程中，不知道全貌就很难判断某一步是否合理。用户无法自然按预设顺序逐节点确认，局部导航不足以提供判断上下文。

### 2. 补齐批注到 Agent 的真实闭环
* **做法**：路径收敛为：多处批注 → 保存 → 按节点/选区汇成一个真实批次 → 复制给 Agent → 回原对话发送 → Agent 受管修改 → 页面原位显示具体变化 → 用户自行核对。
* **收益**：一条也能交接，多条可合批；保存、复制、领取、写入、确认不再混为同一状态。
* **代价**：网页没有自动调用模型，仍有跨到对话发送的步骤。增加按钮提示只能让交接可发现，不能消除这个边界。

### 3. 用实际知识库替代简单演示材料
* **做法**：输入来自 `D:/workspace/pricing_process_review/knowledge_base`，测试任务为 `pricing-knowledge-base-review-smoke`，产出同版 `flow.md`、`model.json`、`review-leads.md` 和 `report.html`。
* **暴露的问题**：实际模型含 31 节点、47 关系、18 疑点、4 个资料分组。长文本、多个入口、分支、汇流和回路让原型的局限显现：完整图缩成细小横条，单步阅读仍缺全貌，批注按钮比内容还抢注意力。

### 4. 图上选范围 ＋ 统一修改面板
* **做法**：点节点、点关系、多选/框选区域；允许直接说哪里不合理，也允许明确执行插入、拆分、编辑、合并或调整分支。
* **收益**：更贴近“先发现问题区域，再提出修改”的实际行为。
* **暴露的问题**：图布局、正文阅读、选区、手动编辑、Agent 意见、状态与历史都挤进同一套工作区，模式切换与解释文字不断增加。

### 5. 四 stage ＋ 横向子流程 ＋ 图上疑点便签
* **做法**：参考 `pricing_process_report.html`，按当前模型的四组展示阶段内从左到右的图，并提供跨阶段入口和出口。保留全图用于跨节点操作。
* **用户反馈**：主区域是一个不错的开始，但顶部大阶段卡浪费垂直空间；右侧仍凌乱；底部一次铺满便签不好看。

### 6. 参考 report 做减法，并增加就地编辑
* **做法**：将 stage 导航收进画布；节点显示角色、名称和工具；详情按“输入/触发 → 操作步骤 → 完成/路径 → 注意事项”排列；选句后才出现批注操作。
* **最终用户判断**：当前版本“有点改废了”，要求归档、回退。因此该版不能被记为已获认可的设计，也不应作为正式 skill 的下一版默认 UI。

## 四、技术上已验证、可单独保留的机制

1. **单一权威内容模型**：图、正文和关系来自同一个 `model.json`；不维护第二份可独立漂移的正文。
2. **稳定身份与依据**：claims、节点、关系、issue 和来源各有稳定 ID。批注保留原目标、版本、精确选文及证据。
3. **真实交接与短生命周期工作包**：继续兼容 `pricing-ref:v1`、`pricing-review-batch:v1`，以及旧批次和受管草稿接口。
4. **并发与版本保护**：原型采用任务级写租约与版本/模型 hash 校验。正文写入互斥，阅读和新增批注仍可继续。
5. **确认独立与变化定位**：展示标题、正文、连接、证据的具体前后变化，保留阅读位置与草稿，而不只是刷新页面或显示“已同步”。
6. **手动条件编辑**：`relation.conditionClaimIds` 本来就承载结构化关联，不必再次让 LLM 猜出已存在的条件。

## 五、为什么不能以“测试通过”作为这条路线成功的证明

1. **把功能完整当成了体验收敛**：不断补齐选区、正文、批注、交接、手动改字、关系编辑、疑点队列、确认、历史和撤销，却没有先验证一个足够简单的主工作方式。
2. **把 report 的视觉优点简化成了样式与 stage 布局**：自动把模型原句装进固定图卡，出现大量截断，再加按钮、状态和滚动，并不能复现同样的理解成本。
3. **同时承载了阅读、改图与 Agent 协作**：drawer 承担正文、范围说明、手工表单、意见输入、疑点、证据和历史，信息与动作彼此争夺空间。
4. **调整了展示，却没有充分检验流程语义本身**：知识库资料的未知与冲突不能通过图形包装消失。
5. **合成测试和浏览器脚本覆盖了“能操作”，没有证明“愿意用、容易懂”**。最后一轮验收应记录为“技术闭环可用，产品方向未通过”。

## 六、回到 0.1.3 之后的建议边界

* **保留作为可参考的需求**：完整正文与来源；句子批注；看结构再提出意见；修改范围明确；真实反馈与用户确认分离；任何切换不丢草稿。
* **保留作为可单独移植的机制**：稳定 ID、真实批次、写入校验、回执清理、确认失效、具体差异。
* **不要整体移植**：当前 drawer 结构、多个编辑模式的组合、底部 memo 墙、把分组直接当业务阶段、依靠截断长句构造图标签。
* **最终判断**：保留研究证据和独立机制，停止把当前原型当作下一版设计继续堆叠。后续从 v0.1.3 重新选择范围，而不是默认延续这条界面路线。
